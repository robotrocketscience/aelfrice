### Added

- **Move locks between scopes, and find the overlap ([#1681](https://github.com/robotrocketscience/aelfrice/issues/1681)).** Nothing merges automatically: you choose what to copy and what to unlock.
  - **Promote:** `aelf lock --promote-user <id>` copies a repository lock into the user store, which the command creates if needed. The id must be exact. The repository lock stays as it is; while it stays locked, this repository injects it in place of the user copy, so to finish the move, run `aelf unlock <id>`. The copy keeps the repository lock's text, tier, and expiry. The row, the tier, and the expiry are written in one transaction, so a failure partway leaves nothing in the user store and the command can run again. Without a user store, the copy is written beside it and moved into place only on success, so a failed promote creates no user store file. Two promotes of the same statement at once add one copy. After that commit, the `belief.locked` feed event is written with `"scope": "user"` and `"promoted_from"`. The command exits 1 without writing when the id isn't an active repository lock, the user store can't be read or created, or the write fails, and it refuses `--doc`, `--category`, `--reference`, `--frozen`, `--for`, and `--until`. When the user store already holds a lock with the same id or a near-duplicate, the command says so, adds nothing, and exits 0. The typed `/aelf:lock` command doesn't take `--promote-user`; run it in a shell.
  - **Doctor:** `aelf doctor` lists the repository locks that near-duplicate a user lock, with the user lock's id and an `aelf unlock <id>` fix line. These are the pairs where the repository copy is injected in place of the user lock. The list doesn't change the exit code. Both stores are read read-only, and a missing user store lists nothing. A store path that can't be checked, such as one under a directory without search permission, makes the list unknown.
  - **Failed typed user locks:** a failed `/aelf:lock --user` request is listed again by `aelf doctor` and counted by the SessionStart notice. It is judged against the user store, so locking the statement in the repository doesn't close it, and its fix line is `aelf lock --user`. The same statement failing in both scopes is two entries. If the user store exists but can't be read, or its path can't be checked, the list says unknown.
  - **Feedback on a shared id:** after a promote, the user copy often has the repository lock's id. `aelf feedback` and `aelf confirm` on such an id now apply to the repository lock, which this repository injects in place of the user copy, and print a note on stderr; the user store is unchanged. They still refuse an id whose repository row isn't a lock, and an id only the user store holds.
  - **Open failures:** `aelf lock --user` and `aelf lock --promote-user` print one line and exit 1 when the user store or its directory can't be opened or created, instead of a traceback.
  - **Core and conflicts:** `aelf core` includes the user locks in its locked group, the same set the hooks inject, tagged `[user]` and with `"scope": "user"` in `--json`. A user lock shows no core admission gate label, because the labels are kept by repository content hash. `aelf search` with `AELF_SHOW_CONFLICTS=1` checks hits against the user locks too; when the conflicting lock is a user lock, the `--json` row carries `"slot_conflict_scope": "user"`.
