### Added

- **Move locks between scopes, and find the overlap ([#1681](https://github.com/robotrocketscience/aelfrice/issues/1681)).** Nothing merges automatically: you choose what to copy and what to unlock.
  - **Promote:** `aelf lock --promote-user <id>` copies a repository lock into the user store, which the command creates if needed. The id must be exact. The repository lock stays as it is; while it stays locked, this repository injects it in place of the user copy, so to finish the move, run `aelf unlock <id>`. The copy keeps the repository lock's text, tier, and expiry, and goes through the `aelf lock --user` write path. Its `belief.locked` feed event carries `"scope": "user"` and `"promoted_from"`. The command exits 1 without writing when the id isn't an active repository lock or the user store can't be read, and it refuses `--doc`, `--category`, `--reference`, `--frozen`, `--for`, and `--until`. When the user store already holds a lock with the same id or a near-duplicate, the command says so, adds nothing, and exits 0. The typed `/aelf:lock` command doesn't take `--promote-user`; run it in a shell.
  - **Doctor:** `aelf doctor` lists the repository locks that near-duplicate a user lock, with the user lock's id and an `aelf unlock <id>` fix line. These are the pairs where the repository copy is injected in place of the user lock. The list doesn't change the exit code. Both stores are read read-only, and a missing user store lists nothing.
  - **Failed typed user locks:** a failed `/aelf:lock --user` request is listed again by `aelf doctor` and counted by the SessionStart notice. It is judged against the user store, so locking the statement in the repository doesn't close it, and its fix line is `aelf lock --user`. The same statement failing in both scopes is two entries. If the user store exists but can't be read, the list says unknown.
  - **Core and conflicts:** `aelf core` includes the user locks in its locked group, the same set the hooks inject, tagged `[user]` and with `"scope": "user"` in `--json`. `aelf search` with `AELF_SHOW_CONFLICTS=1` checks hits against the user locks too; when the conflicting lock is a user lock, the `--json` row carries `"slot_conflict_scope": "user"`.
