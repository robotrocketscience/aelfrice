### Fixed

- **Hook payloads are read as UTF-8 bytes, not locale text ([#1426](https://github.com/robotrocketscience/aelfrice/issues/1426)).** `ensure_utf8_streams` pinned the way *out* in #1329; nothing pinned the way *in*. All eleven stdin read sites — `hook.py`'s four events, the five `_read_payload` helpers in `transcript_logger` / `hook_agent_context` / `hook_claude_memory_mirror` / `hook_commit_ingest` / `hook_search_tool`, the pre-issue guard and the context rebuilder — called `.read()` on a text stream Python had already decoded with the **process locale**. The hook JSON protocol is UTF-8 by definition, so on a Windows console defaulting to `cp1252` a prompt containing `café — 東京 🙂` failed two different ways: the code page raised `UnicodeDecodeError` at the read, or an ASCII locale decoded it through `surrogateescape`, survived the read, and died at the UTF-8 write instead. Both are silent — `main()` catches and returns 0 under the fail-open contract — so the user's turn was simply absent, and compaction reconstruction and belief extraction then ran on incomplete history. A new `stream_encoding.read_payload_text` reads `stdin.buffer` and decodes **strictly**: `errors="replace"` would store something other than what the user typed, and `surrogateescape` only defers the failure to the next write. Streams with no `.buffer` — `io.StringIO`, which every hook's injectable test interface uses — are read as text unchanged, which is what lets one helper serve both paths with no signature churn; pytest's captured-stdin stub raises the same `OSError` it always did. The five `_read_payload` signatures now take `stderr` so the undecodable-payload diagnostic reaches the stream `main()` already threads instead of bypassing it. That diagnostic is bounded and ASCII-only and never echoes the offending bytes, because it is printed onto a stream that may itself be a legacy code page. Six console scripts (`aelf-transcript-logger`, `aelf-commit-ingest`, `aelf-search-tool-hook`, `aelf-agent-context-hook`, `aelf-pre-issue-hook`, `aelf-claude-memory-mirror`) never called `ensure_utf8_streams` at all and now do, closing the #1329 crash on the entry points it missed. The CLI is fixed differently, and the difference matters: `aelf` pins `sys.stdin`'s decoder at entry (`ensure_utf8_stdin`) rather than reading around it. A hook reads its payload exactly once, but `aelf uninstall --archive --password-stdin` calls `input("continue? [y/N]: ")` and *then* reads the password, and those two reads must come off the same layer — `input()` draws the whole pipe into the text wrapper's decode buffer, so a `.buffer` read afterwards finds EOF and the password comes back empty. That covers both CLI sites: `onboard --accept-classifications -` read a pipe through the locale while the branch three lines below read the same JSON from a path with `encoding="utf-8"`, and `--password-stdin` — the one irreversible case, since `lifecycle` derives the scrypt key from `password.encode("utf-8")`, so a non-ASCII password mangled on the way in encrypts an archive against a key that cannot be reproduced from a UTF-8 host. Undecodable password bytes are refused loudly rather than encrypting an archive nobody can open. Reproduced on POSIX with no Windows host: `PYTHONIOENCODING=cp1252` gives a runner the same charmap decoder Windows picks, and `LC_ALL=C` with UTF-8 mode and PEP 538 coercion disabled gives the surrogate path. Note that `PYTHONUTF8=0` alone — the regime the issue's original acceptance test named — reproduces **nothing** and passed on the unfixed tree; a test pins that distinction so a green run of the original criterion is never mistaken for a fix.
