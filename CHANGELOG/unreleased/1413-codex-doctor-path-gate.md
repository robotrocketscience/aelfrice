### Fixed

- **`aelf doctor --host codex` fails when the installed wiring can't reach `aelf`, and the Codex hooks feature is named correctly ([#1413](https://github.com/robotrocketscience/aelfrice/issues/1413), partial).** The Codex hooks and the generated `$aelf-*` skills both invoke the CLI by bare name, so a host whose `PATH` doesn't resolve `aelf` breaks every dispatch at exec — and doctor, the one surface that could have said so, exited 0. It now appends a `[FAIL]` line naming the `uv tool install aelfrice` and `uv tool update-shell` remedy, and exits 1, under the operator ruling of 2026-08-12: the check fires only when `launcher.which_on_path("aelf")` is `None` **and** `report.owned_handler_count` is greater than zero. That gate is the same one [#1430](https://github.com/robotrocketscience/aelfrice/issues/1430) already ratified for this command — absent wiring stays exit 0, so a source checkout and this repo's own CI, neither of which has a `uv tool` install, stay green. `docs/user/SLASH_COMMANDS.md` also told you to turn on a `codex_hooks` feature flag that Codex retired after 0.12x; `codex features list` on codex-cli 0.145.0 reports one row for it, `hooks stable true`, and no `codex_hooks` row at all. The caveat now names `hooks`, says it's on by default, and points at `[features].hooks = false` as the only setting you need to act on; doctor keeps honoring the legacy key when an old `config.toml` carries it, and the doc says so. The rest of the issue — rewriting the 94 `uv run aelf` invocations across the 30 generated skills — stays open, because changing the generated skill bytes makes every already-installed Codex skill differ from the build and needs a Codex host to verify.
