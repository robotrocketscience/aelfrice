### Fixed

- **Mutation testing had never run in CI ([#1457](https://github.com/robotrocketscience/aelfrice/issues/1457)).** `mutation.yml` invoked mutmut with `--paths-to-mutate` and `--tests-dir`, both removed in mutmut 3. Every scheduled run from 2026-06-21 onward died with `Error: No such option '--paths-to-mutate'`, and because both steps ended in a blanket `|| true`, each one reported **success** and uploaded a report containing only the error. The weekly job was a green tick over a command that never executed — the by-hand mutation discipline was the only mutation coverage this project has had. **Configuration alone does not fix it, and this change's own first CI run proved it.** mutmut runs the suite from inside a `mutants/` tree into which it copies `source_paths` plus a fixed set — `tests/`, `pyproject.toml`, the lockfiles — and nothing else, so `[tool.pytest.ini_options] pythonpath = ["."]` resolved to `mutants/`, `import benchmarks` raised `ModuleNotFoundError` during stats collection, and every mutant came back `not checked`: `[tool.mutmut]` correct, harness still dead. `also_copy` now names the repo-root paths the suite actually reads — `benchmarks/`, `scripts/`, `.github/`, `.githooks/`, `docs/`, `CHANGELOG/`, `CHANGELOG.md`, `README.md` — each one found by running the harness rather than reasoned about, because mutmut aborts stats collection on the *first* failing test and so only ever names one missing cause per run. Stated as what a run produces rather than as a property of the config: the stats pass now reaches **7,705 tests inside `mutants/`** where it previously died at zero, and a scoped run (mutmut 3.7.0, `only_mutate = ["src/aelfrice/stream_encoding.py"]`, `mutmut run --max-children 4`) produced **54 mutants — 46 killed, 8 survived, 0 not checked**. **Neither report grep could match anything either.** `mutmut results` prints every line as `print(f"    {k}: {status}")` — four hard-coded, unconditional leading spaces — and both patterns were anchored at `^`, so the weekly guard failed on a healthy tree and the PR job's survivor tally was wired to `0` regardless of the tree. Both are unanchored now (`^ *`, a literal space-star rather than `[[:space:]]*`, so one pattern compiles under grep -E *and* Python `re` and a test can run the extracted pattern against verbatim mutmut output — eight substring assertions over the workflow text is precisely what shipped the anchor). The guard also inferred health from report non-emptiness, which is inverted: `mutmut results` **suppresses killed mutants** unless `--all` is passed, so an empty report is what a fully-killed scope produces. It asserts a positive signal instead — a non-zero mutant total, and no mutant left `not checked`, the state every mutant in that first run was in — over a report taken with `--all=true`. The `=true` is load-bearing: mutmut declares `@click.option("--all", default=False)` with no `is_flag=True`, so click infers a BOOL that *takes an argument*, and a bare `--all` writes `Error: Option '--all' requires an argument.` into the report — the same shape of swallowed usage error as the original defect, and found only by running it. Survivors are counted on `: survived$` and the harness statuses (`no tests`, `timeout`, `suspicious`, `skipped`, `not checked`) tallied separately, so a number meaning "the harness got no answer" is never read as coverage. Added alongside it: an advisory per-PR job scoped through `only_mutate` to the **merge-base** diff (`BASE...HEAD` — the two-dot form is the difference between two trees and would mutate every file `main` moved since the branch point). mutmut is pinned `>=3,<4` in both jobs, since `source_paths`, `only_mutate`, `--max-children` and the report format the greps parse are all mutmut-3 shapes and an unpinned major bump is the exact failure this workflow exists to catch. The job carries a name rather than reporting as the bare id `diff`, and its `continue-on-error` is asserted to be at *job* level — this is the repo's first job-level use, every existing one is step-level, and a step-level flag leaves the job's check-run at `failure`, which is what blocks the train.
