### Fixed

- **`BASH_FIRE_CAP_PER_TURN` now binds, because its counter moved to a per-session map in the session ring ([#1522](https://github.com/robotrocketscience/aelfrice/issues/1522)).** The declared ceiling of three retrieval-performing Bash searches per turn could not be reached in any deployed configuration. `aelf-search-tool-hook` is registered as a `"type": "command"` hook, so the host spawns one OS process per fire; the counter was a module-level dict, empty at the start of every one of them. Five processes in one session performed five retrievals where one process performed three, and the source comment naming it a "per-process per-turn" counter stated the assumption that fails: per-process and per-turn are not the same scope here. The count now lives in `session_ring.py` — already flock-guarded, atomically written and beside the store — under a `bash` map keyed by `session_id`, holding `turn_id` / `fires` / `fires_turn_id` / `seq` per session, and the `UserPromptSubmit` hook stamps that session's turn boundary, being the only hook guaranteed to fire exactly once per turn. The count names the turn it was taken in and a reader reports zero fires as soon as the two disagree, so the reset is a consequence of that comparison rather than a second write a crash between the two could skip — the cap resets each turn instead of becoming the permanent per-session cap of three that a naive move-it-to-a-file fix would have shipped.

  A *map* rather than three fields on the ring record, because the record is one per repo checkout, keyed by a single `session_id`, and a write from a different session replaces it wholesale. Every git worktree of a repo shares one `session_injected_ids.json`, and several concurrent sessions against it is a normal configuration, so counters held in that record are zeroed by any neighbour's fire: an A,A,A,B,A,A,A interleave of real hook processes emitted 7 of 7 blocks, six of them session A's, against a cap of 3. `scripts/bash_fire_cap_latency.py interleave` runs that sequence against both designs — 7 of 7 for a record-scoped counter, and 4 of 7 for the per-session map this ships, being A's three plus B's first. The map survives the record reset that a session switch performs, is bounded to `BASH_STATE_MAX_SESSIONS` (8) entries evicted least-recently-touched-first so one file serving a machine's worth of sessions cannot grow without limit, and a turn stamp bumps only the stamping session's `turn_id` — a prompt submitted next door does not re-open this session's budget.

  Every ring failure (absent, malformed, unwritable, no record yet, no `session_id` in the payload) degrades to "no cap", never to "cap reached": a hook that suppressed retrieval because it could not read a file would be worse than the unbounded firing this bounds. Two overshoots follow from that direction and are documented in the spec rather than closed: a payload with no `session_id` is uncapped, and the read is lock-free, so Bash calls dispatched in parallel can each see the same count and exceed the cap by that parallel width.

  The cap check also moved behind `_extract_bash_query`, which imports nothing: consulting the ring pulls `session_ring` -> `db_paths` -> `store`, and ordered ahead of extraction that cost landed on *every* Bash tool call in the session rather than on the few that are searches. Every figure below comes from `scripts/bash_fire_cap_latency.py`, which is in this branch so each one has a command that re-derives it (#1469). `bash_fire_cap_latency.py order --pairs 60` copies `src/` twice and swaps those two statements in one copy, so both arms are real source trees differing only in that order, and runs one cold hook process per sample with the arms interleaved: a non-search Bash call is 26.0 ms median in the shipped order against 40.1 ms with the cap check first, a 14.0 ms median paired delta that was positive in 60 of 60 pairs. `python -X importtime -m aelfrice.hook_search_tool` confirms the mechanism rather than the timing — `cat notes.txt` imports `aelfrice.session_ring` 0 times, `rg needleprobe src/` imports it once. Against that, `bash_fire_cap_latency.py cap --pairs 40` puts a suppressed fire 168.7 ms below a firing one — 209.5 ms against 39.9 ms, positive in 40 of 40 pairs — against an empty store, where a populated store makes the firing arm heavier still. A ten-`rg` turn therefore stops paying roughly 1.2 s of hook latency serialized ahead of the user's own tool calls.

  Read those figures as this machine's, not as constants. They are wall-clock on one developer laptop that other work was sharing, and both absolute medians move with that load: five runs of the reorder probe put its paired delta between 12.1 and 14.0 ms, and four runs of the suppression probe put its saving between 151.5 and 168.7 ms, which is what makes the ten-`rg` consequence a 1.1-1.2 s band rather than a constant. What holds across runs is the sign, which was unanimous in every run of both probes.

  What the cap costs is that the fourth and later allowlisted searches in a turn get no injection at all, and the value 3 dates from #213 — it has not been re-derived against how many searches a turn issues today. That share is not measurable from the shipped telemetry: `search_tool_hook.jsonl` records a `session_id` per fire but `user_prompt_submit.jsonl` records no `session_id`, so fires cannot be attributed to turns without the hook audit log. Raising the value is a one-constant change once that attribution exists.

  The regression tests are subprocess-driven, one process per fire with a distinct search token each, because an in-process test structurally cannot observe either defect — it passes against the dead counter and the wired ring alike, which is how the cap shipped non-functional, and it cannot interleave two sessions against one ring file at all.
