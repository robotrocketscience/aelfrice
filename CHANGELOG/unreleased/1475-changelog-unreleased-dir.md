### Changed

- **Unreleased changelog entries are one file each, collated at release ([#1475](https://github.com/robotrocketscience/aelfrice/issues/1475)).** Thirteen of fourteen open PRs on the 2026-08-10 board inserted into `CHANGELOG/v4.md` within lines 8-16 — one contiguous overlap region, so draining that queue serially cost eleven hand resolutions, and the repo's standing rule is never to auto-resolve them. Entries are single lines of 2,000-4,500 characters, so git offers two 4 KB lines with no intra-line granularity and an entry dropped during the resolution leaves no trace in the diff: silent data loss on the file whose entire purpose is the record of what shipped. New entries now go in `CHANGELOG/unreleased/<issue>-<slug>.md`, one file per entry; `scripts/collate_changelog.py` folds them into the dated section at release time and empties the directory. Add/add on distinct paths never conflicts, so the tax goes to zero rather than down. The claim is run, not asserted — `tests/test_changelog_merge_shape.py` drives real `git merge` in a scratch repository and shows the same two entries conflicting in the block (`CONFLICT (content)`, `UU CHANGELOG/v4.md`) and merging clean as two files.

  **The transition is non-breaking, and the `[Unreleased]` block was deliberately not touched.** Editing it would have made this change conflict with all thirteen in-flight PRs and defeat its own purpose. Collation emits the block first within each category and then the files, so a PR already editing the block still releases correctly and never has to rebase onto the new convention to merge. Ordering is deterministic and filesystem-independent: Keep-a-Changelog category order, block entries in file order, then entry files sorted by name — never `glob` order, never mtime.

  **The honest cost is that this moves a failure from merge time to release time**, from loud (a conflict you cannot commit through) to quiet (an entry that silently never appears), so the two ways collation can lose an entry are pinned before it ships: exactly one entry per input file reaches the output, and the directory is empty after a cut. Both were mutation-checked. `release-docs-check` now fails a release PR that strands an entry file, the same way it already fails one that leaves `[Unreleased]` undrained, and `scripts/check_changelog_dupes.py` compares entry files against each other and against the block in one corpus rather than one file at a time — per file there is exactly one entry and never a duplicate, so a per-file check would have reported a pass having examined nothing that could fail.
