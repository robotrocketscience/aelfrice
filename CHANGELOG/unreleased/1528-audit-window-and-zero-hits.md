### Fixed

- **The hook audit log records its own truncation, and the zero-hit fire it was silently dropping ([#1528](https://github.com/robotrocketscience/aelfrice/issues/1528)).** `hook_audit.jsonl` is the substrate this project measures itself with — [#1407](https://github.com/robotrocketscience/aelfrice/issues/1407) exists so per-fire outcomes are counted rather than inferred — and two properties of the writer made every rate derived from it narrower and more optimistic than it looked. Both defeated that intent the same way: they made an absence indistinguishable from a measurement.

  **Rotation was destructive and silent.** Rollover is an append-then-`os.replace` into a single slot `hook_audit.jsonl.1`, so the second rollover overwrites the first archive and that history is gone. Nothing in the surviving files said so, and a benchmark reading `hook_audit.jsonl*` could not tell a short history from a truncated one. Retention was deliberately **not** widened — N slots multiply the on-disk cost by N on every repo that has an audit log, and the property the issue asks for is detectability, not retention. Each rollover now stamps one `{"hook": "audit_rotation"}` row as the first line of the freshly emptied live file, carrying that file's generation number, a summary of the file just retired (row count and `ts` range), and the one fact nothing else can reconstruct: how many archives have already been discarded.

  **The answer is three-valued, and the third value is what makes it honest.** `audit_window()` reads the markers back as a generation, a `records` count, a first/last `ts`, and a pair of flags: `truncated` when archives are provably gone, `complete` when nothing was discarded and that is provable, and *neither* when the files cannot settle it. The first rollover is `complete` — it fills an empty slot and destroys nothing, and a warning that fired on every rotated log would be no signal at all. A `.1` carrying no generation stamp is the unknown case, and it is the common one: every log already rotated in the wild predates this marker, so one rollover discarded nothing and a second discarded the first archive, and no surviving file can say which. **When such a log next rolls over, the writer reads the doomed `.1`'s existence before the `os.replace` removes it** and stamps `discarded_generations: 1, discarded_unknown: true` — at least one archive destroyed, true count unknowable. Without that read the live file scans as generation 1, and the very rotation that destroyed 10.5 MB of history would have claimed to discard nothing. "Unknown, at least one destroyed" is a truthful answer; "nothing discarded" is not.

  **The zero-hit population was never recorded.** On the `UserPromptSubmit` path the audit write lived inside `if hits:` and `elif gate_skip:`. A fire where retrieval ran and returned zero hits, with the shape gate not firing, matched neither and wrote **no row**. That is exactly the population an analysis wants most — the prompts where retrieval did full work and found nothing — so every hit rate, fires-per-session and cold rate computed from this log had that class missing from its denominator with nothing indicating the gap. Such a fire now writes one row of the same shape with `n_beliefs: 0`, an empty `beliefs[]`, and no `prompt_shape_gate_skip` key, so it is a measured zero rather than a hole and is not confused with the gate-skipped bucket. It carries `sidecar_outcome` and `order_policy` for the same reason the gate-skip branch does: a zero-hit fire can still have paid a full rebuild, and that is the fire [#1380](https://github.com/robotrocketscience/aelfrice/issues/1380) is priced on. The zero covers both "BM25 found nothing" and "the project-context, session-exclusion and category filters emptied what it found" — both are a fire that injected nothing, which is what a hit rate's denominator needs; separating them would need a pre-filter count and is out of scope here. The `hook.py` edit is one `else` branch and nothing else, because another change is in flight against that file.

  **`benchmarks/sidecar_rebuild_rate.py` states the window it covered** — first and last row timestamp, whether a `.1` was present, the rotation generation — above the rate. It prints `WINDOW TRUNCATED` with the discarded count when generations are gone, `at least N` when that count is a floor, and `WINDOW UNKNOWN` for a `.1` with no generation stamp. Two ways it could contradict itself are closed: the completeness wording is gated on the generation rather than on a `.1` being among the paths, so a marked live file passed alone no longer prints "no rotation has occurred" under "rotation generation 2"; and an archive handed in without its live file reports unknown rather than complete, because each file records what had been lost when it was *created* and is blind to the loss caused by the rotation that archived it.

  **Compatibility and cost.** Every existing reader filters on a specific `hook` value, so the marker row is inert to all of them and is excluded from the benchmark's row census explicitly. A log with no marker and no `.1` has never rotated and reads as exactly complete; one with a `.1` reads as unknown — and the `.1` counts whenever it is on disk beside the live file, not only when the caller passed it in, because the single-path invocation is the documented one and every log already rotated in the wild is unmarked; `audit_window()` skips missing, unreadable, non-object and unparseable lines rather than raising. Disk is unchanged at two files — a `.2` slot is still never created. The scan runs once per rotation, which is once per `max_bytes` of accumulated log. Measured against a synthetic file at the 10 MiB default cap — 10.00 MiB, 9,939 rows, medians of 7 — it costs **31.2 ms** on the single fire that rotates, so **0.0031 ms** amortised across the 9,939 fires that filled the file, and the marker row is **275 bytes**, 0.0026% of the cap. Read those as one corpus, not as constants: the scan parses every row, so its cost tracks row CONTENT as well as file size, and `[hook_audit] max_bytes` is operator-settable, so a larger cap costs proportionally more per rotation and proportionally less per fire. Quote the ratio rather than the milliseconds for any other cap or corpus. The scan parses every row because `first_ts`/`last_ts` are a true min/max: concurrent hook processes append to this file, so reading the first and last line instead would be an ordering assumption rather than a measurement. A byte-oriented newline count over the same file is roughly an order of magnitude cheaper at **3.7 ms**, but yields only the row count.
