### Fixed

- **The hook audit log records its own truncation, and the zero-hit fire it was silently dropping ([#1528](https://github.com/robotrocketscience/aelfrice/issues/1528)).** `hook_audit.jsonl` is the substrate this project measures itself with — [#1407](https://github.com/robotrocketscience/aelfrice/issues/1407) exists so per-fire outcomes are counted rather than inferred — and two properties of the writer made every rate derived from it narrower and more optimistic than it looked. Both defeated that intent the same way: they made an absence indistinguishable from a measurement.

  **Rotation was destructive and silent.** Rollover is an append-then-`os.replace` into a single slot `hook_audit.jsonl.1`, so the second rollover overwrites the first archive and that history is gone. Nothing in the surviving files said so, and a benchmark reading `hook_audit.jsonl*` could not tell a short history from a truncated one. Retention was deliberately **not** widened — N slots multiply the on-disk cost by N on every repo that has an audit log, and the property the issue asks for is detectability, not retention. Each rollover now stamps one `{"hook": "audit_rotation"}` row as the first line of the freshly emptied live file, carrying that file's generation number, a summary of the file just retired (row count and `ts` range), and the one fact nothing else can reconstruct: how many archives have already been discarded. `audit_window()` reads it back as a generation, a `records` count, a first/last `ts`, and a `truncated` flag. The first rollover reports `truncated=False` — it fills an empty slot and destroys nothing, and a warning that fired on every rotated log would be no signal at all.

  **The zero-hit population was never recorded.** On the `UserPromptSubmit` path the audit write lived inside `if hits:` and `elif gate_skip:`. A fire where retrieval ran and returned zero hits, with the shape gate not firing, matched neither and wrote **no row**. That is exactly the population an analysis wants most — the prompts where retrieval did full work and found nothing — so every hit rate, fires-per-session and cold rate computed from this log had that class missing from its denominator with nothing indicating the gap. Such a fire now writes one row of the same shape with `n_beliefs: 0`, an empty `beliefs[]`, and no `prompt_shape_gate_skip` key, so it is a measured zero rather than a hole and is not confused with the gate-skipped bucket. It carries `sidecar_outcome` for the same reason the gate-skip branch does: a zero-hit fire can still have paid a full rebuild, and that is the fire [#1380](https://github.com/robotrocketscience/aelfrice/issues/1380) is priced on. The `hook.py` edit is one `else` branch and nothing else, because another change is in flight against that file.

  **`benchmarks/sidecar_rebuild_rate.py` states the window it covered** — first and last row timestamp, whether a `.1` was present, the rotation generation — above the rate, and prints `WINDOW TRUNCATED` with the discarded count when generations are gone. A `.1` carrying no generation stamp reports `WINDOW UNKNOWN` rather than complete: logs already rotated in the wild have no marker, one rollover discards nothing and a second discards the first archive, and the files cannot say which. Claiming completeness there would be the exact unearned claim this change exists to prevent.

  **Compatibility and cost.** Every existing reader filters on a specific `hook` value, so the marker row is inert to all of them and is excluded from the benchmark's row census explicitly. A log with no marker anywhere degrades to generation 1 with nothing known discarded, which is the only claim such a file supports; `audit_window()` also skips missing, unreadable, non-object and unparseable lines rather than raising. Disk is unchanged at two files — a `.2` slot is still never created. Measured on this branch against a synthetic 10.00 MiB file (the default cap) holding 5,143 realistic audit rows: the rotation scan costs **43.8 ms** on the single fire that rotates, **0.0085 ms** amortised per fire, and the marker row is **225 bytes**, or 0.0021% of the cap. The scan parses every row because `first_ts`/`last_ts` are a true min/max — concurrent hook processes append to this file, so reading the first and last line instead would be an ordering assumption rather than a measurement; the byte-oriented alternative runs in 6.3 ms but yields only the row count.
