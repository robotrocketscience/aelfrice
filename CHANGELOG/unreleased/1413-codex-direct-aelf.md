### Fixed

- **Generated Codex skills invoke `aelf` directly instead of wrapping it in `uv run` ([#1413](https://github.com/robotrocketscience/aelfrice/issues/1413)).** Every `$aelf-*` skill `aelf setup --host codex` generates carried the `uv run aelf …` form — 96 occurrences across all 31 skills — which added a writable-cache requirement to a CLI that is already on `PATH`. `uv run` initializes and locks its cache before aelfrice starts, so in a Codex sandbox whose cache is read-only the skill fails at the wrapper: measured on this host, `uv run aelf --version` exits 2 with ``failed to open file `…/CACHEDIR.TAG`: Permission denied`` where `aelf --version` exits 0. It also resolves a project environment, so an unactivated checkout holding a different aelfrice version silently shadowed the `uv tool` install that generated the skill. `codex_skill_from_slash` now rewrites the invocation at transform time, which is where it belongs: the bundled slash bodies are shared with the default host, where `uv run` is correct for a source checkout, so the bundle is unchanged and only the Codex port is rewritten. No absolute path is baked in — the skill resolves `aelf` through the invoking shell's `PATH`, so one generated bundle stays valid across machines and across the POSIX and Windows shim families. **This deliberately ends the "body carried through verbatim" invariant**, which `tests/test_codex_skills.py` and `docs/user/SLASH_COMMANDS.md` both asserted; the amended test pins that the rewrite is the *only* difference, so nothing else in the body can be edited, reordered, or dropped unnoticed. Existing Codex installs keep their old skill text until you re-run `aelf setup --host codex`; `aelf doctor --host codex` already reports that case as a fault naming the skills and the command to run.
