### Fixed

- **The injected memory block is bounded again, and user locks are exempt from the bound ([#1551](https://github.com/robotrocketscience/aelfrice/issues/1551)).** `DEFAULT_HOOK_TOKEN_BUDGET = 1500` is passed to `retrieve()` and the packers in `clustering.py` honour it, but `<locked>`, `<core>`, `<recent-work>` and the retrieval hits are packed independently and concatenated, so no budget bounded the block that reached the model. `_write_hook_audit_record` already measured the result with the same 4-chars-per-token estimator the budgeter uses and wrote the overrun to `hook_audit.jsonl`; nothing acted on it.

  **One write path.** Every `<aelfrice-memory>` write now goes through `_write_memory_block`, which trims, notes and emits. Three sites emit that envelope — `user_prompt_submit`'s retrieval branch, its `elif gate_skip:` branch, and `session_start` — and only the first was ever bounded. The gate-skip branch ships a session's whole `<locked>` and `<core>` sub-block whenever the #674 prompt-shape gate refuses BM25 on a first prompt (a first prompt under 12 characters, an acknowledgement), which on shipped defaults is routine: 17,201 estimated tokens from 300 user locks of 159 characters — `"lockword "` plus 150 characters of padding — against a 6,000-token ceiling, with nothing on stderr. Re-derive with `uv run python scripts/measure_block_ceiling.py --gate-skip`, which seeds that fixture and disables the ceiling; `--emit-figures` publishes the same number so CI re-runs it.

  **The drop policy: both bounds stop at `lock="user"`.** `enforce_block_ceiling` drops whole `<belief>` elements until the body fits `HOOK_BLOCK_TOKEN_CEILING`, and never drops a user-locked one; `_cap_belief_content` truncates one belief's content at `BELIEF_CONTENT_CHAR_CAP = 1200` at each render site — the retrieval hits, `<core>`, and the non-locked entries of `<locked>` — and never truncates user-locked content. That is the #379 / #1016-B contract: locks are the always-injected pool, and a bound that deleted them would have been the thing that broke it. An earlier revision of this change did exactly that — on a 300-lock store all 300 locked elements were removed, leaving an empty `<locked>` section under 300 dangling `seen <id>` manifest pointers. A block that cannot fit without dropping a lock is emitted over the ceiling with a one-line note on stderr naming the overrun and saying that no further span was droppable. That note used to prescribe `aelf lock --reference`, and the advice was withdrawn after it was measured: `_build_session_start_subblock`'s `<locked>` loop renders every lock verbatim with no `is_reference_lock` branch, so on a session's **first** prompt the tier changes nothing. On one 30,026-character lock the gate-skip branch emits 7700 estimated tokens and the retrieval branch 7796 — identically frozen and reference, the retrieval branch carrying the full text *and* a `ref` pointer to it in the same envelope. From the second prompt the sub-block is gone, `_split_belief_lines` renders the locks and the tier does bound: 256 tokens against 7683. `session_start`'s own baseline path honours it too (233 against 7660). The whole table is `scripts/measure_block_ceiling.py --reference-tier`, whose module constant is the fixture; the three manifest-bearing figures depend on the lock's content, not only its length. A note that prescribed the tier would therefore be wrong exactly where a lock-only store overruns, and `_write_memory_block` sees only an assembled body, so it cannot tell the cases apart. The render gap is [#1558](https://github.com/robotrocketscience/aelfrice/issues/1558), and the note cites it instead of prescribing anything. The only spans ever removed are complete elements and the `seen` pointers that name them — the paragraph below is why the pointer goes with its element — so every framing tag, including the `<aelfrice-locks-manifest>` wrapper, is untouched and the block stays well-formed, and the ids of anything dropped are returned so the audit record, the `injection_events` rows, the session ring, `belief_touches` and the #1382 ledger credit only what was actually emitted.

  **The shed order is by lane, so the prompt's own hits go last.** The lanes are emitted `<locked>`, `<core>`, `<recent-work>`, per-turn hits, so a dropper that took the end of the body took the retrieval hits *this prompt* selected and kept the `<core>` pool the prompt had no part in choosing — `<core>` ranks by corroboration and posterior, `<recent-work>` by the git state of the checkout, and neither consults the prompt. The removal order is now `<core>` tail-first, then `<recent-work>`, then the hits, with locks undroppable throughout; within a lane it is still tail-first, because each lane is already sorted worst-last. Measured on 50 user locks of 150 characters, 20 `<core>` beliefs without the query term and 20 hits with it — re-derive with `uv run python scripts/measure_block_ceiling.py --lanes` — the block carried 6/20 hits and 19/20 core untrimmed, 0/20 and 17/20 under the old order, and 6/20 and 7/20 under the new one: every hit the untrimmed block had, and the bytes taken out of the lane the prompt did not choose.

  **A dropped element takes its `seen` pointer with it.** The dangling pointers above were an instance of a wider class, not a locks-only accident: any dropped element that another line points at leaves the pointer behind. `retrieval.seen_manifest_line` states the contract — the entry exists because "the full text is already in this context window, above" — so a `seen <id>` line whose element the trim deleted tells the model to look up text that is not in the block. On a session's first prompt #1547's dedupe puts both halves in one envelope, rendering a belief verbatim in `<core>` and as a pointer among the per-turn hits, and a `<core>` element carries no `lock="user"`. Measured against the shipped 6,000-token ceiling, on stores of user locks of 150 characters plus corroborated beliefs of 2,000: 80 locks plus 20 such beliefs gave 82 `seen` ids against 80 elements, 2 dangling; 70 plus 30 gave 72 against 70; 60 plus 40 gave 62 against 61. A core-only control of 40 beliefs of 4,000 characters fits under the ceiling and gives 4 against 4, dangling nothing. Every one of those is 0 dangling with the pointer removal in place. `enforce_block_ceiling` now removes the pointer with the element rather than exempting a pointed-at element from the drop, because exempting it would let a size optimisation pin bytes in place — on a first prompt where every `<core>` entry is also a hit, that is the whole droppable set. A pointer to a belief rendered on an earlier turn is untouched: no element in this body carries its id.

  **The ceiling is a real limit, not an unreachable one.** An earlier revision of this entry and of the constant's docstring said it was "set well above the sum of the per-lane budgets so it does not fire on a healthy store". That was not measured and is false: on a session's first prompt, where the `<locked>` sub-block and the per-turn hits share one envelope, it first reports at 66 user locks of 150 characters and at 58 of 200 — re-derive with `uv run python scripts/measure_block_ceiling.py --lock-chars 150 200`. Override with `AELFRICE_HOOK_BLOCK_CEILING`; only a literal `0` disables it, and a negative or unparseable value falls back to the default with a note rather than silently removing the backstop, which `-1` used to do.

  **A dropped belief stays unexplored.** `search_for_prompt` writes one `feedback_history` row per hit tagged `source='hook'`, and that row is this codebase's exposure record: `store.exploration_pool` (#1176) draws beliefs that have none, so a row written for a belief the model never saw evicts it from the never-shown pool for good, and #1279's slot exists because a belief with no exposure can never earn its way into a pack. The row was written inside `_retrieve`, before the block was assembled and the ceiling had run. Measured on a store of 60 user locks of 150 characters and 20 hits of 412, one fire on shipped defaults: 3 elements dropped, all 3 collecting a row and a `last_retrieved_at` stamp, and the pool falling 20 to 14 with 3 of the 6 departures never rendered. The write now happens at the emit boundary against the emitted set — 63 rows, none unrendered, pool 20 to 17. It moves whole rather than in pieces, so `record_retrieval` keeps resolving one timestamp for the audit row and the `last_retrieved_at` mirror inside a single transaction, which is #1373's invariant. `_retrieve` no longer takes a `record_exposure` parameter: nothing visible from inside it decides whether the model saw a belief.

  **One accounting write stays upstream of the ceiling, and now says so.** The `exploration_events` row (#1279) is written where the draw is made, before the block is assembled, so on an over-ceiling block it can name a belief the model never saw: the drawn belief is appended to the tail of the pack and the per-turn tail is what the ceiling sheds first. Measured at the shipped ceiling on a 60-lock / 20-core / 12-hit store (`scripts/measure_block_ceiling.py --exploration`), the emitted block was identical with the slot on and off at 5923 estimated tokens while the ledger recorded one draw and one displacement, 0 of which reached the model. The row is kept where it is — it is the replay record of a pack decision, and a ledger that skipped the fires whose draw was dropped would be missing exactly the fires an operator re-deriving a seed goes looking for — and `_substitute_exploration_slots`, `docs/user/CONFIG.md` and a wiring test now all state the asymmetry. It costs a coverage figure counted from `drawn_ids` alone, which over-counts; the join against `injection_events` that CONFIG.md already specifies is correct, because that write moved to the emit boundary here.

  **The exploration slot prices its displacement in the same currency.** #1279 substitutes a never-injected belief for enough of the non-locked tail to pay for itself, and computed both sides with `retrieval._belief_tokens` — the whole of a belief's content, which this lane stopped emitting when the per-belief cap landed. On a 35,012-character belief the lane's own `_ups_belief_line_cost` charges 314 tokens against that function's 8,766, so a drawn belief over the cap demanded displacement it would never occupy and a displaced one was credited with freeing budget already trimmed out of the block. Both sides now charge `_ups_belief_line_cost`.

  The UserPromptSubmit lane also charges the line it renders. It passes `hook._ups_belief_line_cost` to `retrieve()` as `belief_cost_fn`, the counterpart of `hook_search_tool._belief_line_cost` on the PreToolUse lane (#1526 item 4). Without it the packer charged the whole of a belief's content while the renderer emitted at most `BELIEF_CONTENT_CHAR_CAP` of it, so a 35,012-character belief cost 8,766 tokens against a budget of 1,500, was rejected outright, and the fire injected an **empty block** — the cap never ran, on the lane the cap was added for. The same belief renders a 1,280-character element and now costs 321, admitted and capped.

  Re-tuning `DEFAULT_HOOK_TOKEN_BUDGET` itself is still not attempted: that needs a retrieval-quality gate rather than a byte count, as that constant's docstring already flags. A capped belief keeps its id, so its full text stays reachable through `aelf search` or an anchored document.
