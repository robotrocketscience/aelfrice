### Fixed

- **The merge-train reads the whole pull-request body before closing the issues it links ([#1541](https://github.com/robotrocketscience/aelfrice/issues/1541)).** Step 7/7 exists because this repo's signed-commit branch protection requires a fast-forward push, and a fast-forward does not trigger GitHub's own auto-close; the step parses `Closes #N` out of the body and closes each match. It piped that body through `head -c 8192` **before** matching, so a keyword written past the 8,192nd byte was truncated away and its issue stayed open. The failure is silent in both directions a reader would check: the merge succeeds, and the train logs `no linked issues parsed from PR body` — the same line a PR that genuinely links nothing produces. Measured on the real bodies of the last four merges, old parse against new: `#1537` (11,823 B, keyword at byte 463) `[1522] → [1522]`; `#1538` (11,242 B, byte 9,148) `[] → [1513]`; `#1539` (9,698 B, byte 8,992) `[] → [1469]`; `#1543` (17,397 B, byte 0) `[1369] → [1369]`. Both bodies over the cut lost their close, and [#1513](https://github.com/robotrocketscience/aelfrice/issues/1513) and [#1469](https://github.com/robotrocketscience/aelfrice/issues/1469) were closed by hand afterwards. **No input cap replaces the old one.** The cap was the defect: `grep` streams, and the unbounded quantity was never the body but the loop over what came out of it, which is bounded by how many distinct issues one person wrote in one description. Re-adding a larger cap would re-introduce the same bug at a larger offset, so a surprising count now warns on stderr and drops nothing. The parse moves into `scripts/merge_train_linked_issues.py` so it can be tested at all, matching the precedent [#1397](https://github.com/robotrocketscience/aelfrice/issues/1397) set for the gate decision; `tests/test_merge_train_linked_issues_1541.py` pins a keyword found at byte 0, 463, 8,172, 8,192, 8,992, 9,148 and 65,536, and carries the old cut as an explicit control so the offsets cannot stop straddling the truncation they were chosen to straddle. Two tests read the workflow itself, with `#` comment lines stripped — the comment explaining the defect necessarily quotes the pipeline that caused it, and a naive substring search finds the bug in its own postmortem. Five mutations were run and all five go red: truncating the parse again, dropping the regex's leading `\b`, letting the keyword match without whitespace, silently capping the output, and re-adding the truncating pipe to the workflow. **Two fidelity gaps are documented and deliberately left.** The keyword set is `closes` / `fixes` / `resolves`, narrower than the nine GitHub acts on, so `Fixed #N` does not close here though a merge commit would have closed it; and fenced code blocks are not excluded, so a body demonstrating the syntax closes the issue it names. One misses a close and the other makes a wrong one. Both change which issues close rather than whether the body is read, which is why neither is taken here.
