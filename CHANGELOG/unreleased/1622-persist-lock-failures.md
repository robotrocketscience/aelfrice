### Added

- **A typed `/aelf:lock` that fails now stays visible until you apply it ([#1622](https://github.com/robotrocketscience/aelfrice/issues/1622)).** Since [#1626](https://github.com/robotrocketscience/aelfrice/issues/1626) the `UserPromptSubmit` hook runs a typed lock itself and reports a failure in that turn, but nothing reported it afterwards. The hook now records each typed lock's outcome in `command_outcomes.jsonl`, next to the store, immediately after the command returns and before retrieval runs, so an exception or a timeout in retrieval cannot drop the record. Each row carries the outcome reason, a SHA-256 of the statement, its length, the session, and a prefix of the statement for display. `aelf doctor` has a new section, shown on every run, that lists each lock that failed with an exception or a non-zero exit and is still not locked, with its statement and the command that fixes it. A row keeps only the first 500 characters of a statement, so for a longer statement `doctor` prints no command and asks you to run `aelf lock` with the full statement: a command built from the prefix would lock text you never typed. SessionStart prints one line while any such lock remains. Input errors that the turn already reports (an empty argument, an argument over the length cap, an argument that starts with `-`, an argument that is not valid Unicode text) are recorded but are not listed. The store decides when a lock is resolved: a gap closes when the statement's `content_hash` is locked and active, which covers a lock you apply later from the CLI, or when the belief has a later `lock:unlock` or `lock:expire` row, or you later retire or delete it with `aelf retire` or `aelf delete`. A lock you remove on purpose is not reported as missing. When the hook audit is disabled (`AELFRICE_HOOK_AUDIT=0` or `[hook_audit] enabled = false`), when no hook audit exists beside the store, or when the store cannot be read, `doctor` reports `unknown` and the reason, not zero. The section is informational and does not change `doctor`'s exit code. `CommandOutcome` gains a `reason` field (`CommandReason`), so callers no longer have to read the prose line to tell an input error from a failed command. **The check is forward-only:** it covers locks typed after you upgrade. Earlier failures have no recorded outcome and are not listed.
