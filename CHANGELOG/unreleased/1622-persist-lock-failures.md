### Added

- **A typed `/aelf:lock` that fails now stays visible until you apply it ([#1622](https://github.com/robotrocketscience/aelfrice/issues/1622)).** Since [#1626](https://github.com/robotrocketscience/aelfrice/issues/1626), the `UserPromptSubmit` hook runs a typed lock itself and reports a failure in that turn, but nothing reports it afterwards. The hook now records each typed lock's outcome, and `aelf doctor` and SessionStart show every failed lock that is still not applied.

  - **Recording:** the hook writes each outcome to `command_outcomes.jsonl`, next to the store, immediately after the command returns and before retrieval runs, so an exception or a timeout in retrieval can't drop the record. Each row holds the outcome reason, a SHA-256 of the statement, its length, the session, and the first 500 characters of the statement.
  - **Reporting:** `aelf doctor` has a new section, rendered on every run, that lists each lock that failed with an exception or a non-zero exit and is still not applied, with its statement and the command that fixes it. SessionStart prints one line while any such lock remains. The section is informational and doesn't change `doctor`'s exit code.
  - **No command for a statement it can't reproduce:** for a statement longer than 500 characters, `doctor` prints no command and asks you to run `aelf lock` with the full statement, because a command built from the prefix would lock text you never typed. For a statement that contains an unpaired surrogate, it asks you to retype it.
  - **Input errors aren't listed:** the turn already reports an empty argument, an argument over the length cap, an argument that starts with `-`, and an argument that contains an unpaired surrogate. The hook records these, but `doctor` doesn't list them.
  - **The store decides when a lock is resolved.** A gap closes when one of these holds:
    - a belief with the statement's hash is locked at user level and active, which covers a lock you apply later from the CLI;
    - the belief has a `lock:unlock` or `lock:expire` row later than the failure;
    - you retire or delete the belief with `aelf retire` or `aelf delete` after the failure, and it stays retired or deleted. If you run `aelf restore`, the statement is back and unlocked, so the gap is listed again;
    - you lock the statement from the CLI after the failure and then delete it. This still holds after `aelf doctor --gc-orphan-feedback --apply` removes the delete's own audit row, because the detector reads the later `aelf lock` from `ingest_log`.
  - **"Later" means a later second:** the outcome's timestamp has whole-second resolution, so a removal stamped in the same second as the failure might have come first, and the gap stays open. Timestamps are compared as instants, so the `lock:expire` format (microseconds and `+00:00`) compares correctly with the others.
  - **Unknown is reported as unknown:** `doctor` reports `unknown` and the reason, not zero, when the hook audit is disabled (`AELFRICE_HOOK_AUDIT=0` or `[hook_audit] enabled = false`), when no hook audit exists beside the store, when the store can't be read, and when the store is in memory.
  - **Breaking for direct callers of `CommandOutcome`:** it gains a required `reason` field (`CommandReason`) and optional `command` and `argument` fields, so a two-argument `CommandOutcome(line, took_effect)` no longer constructs. Branch on `reason` to tell an input error from a failed command, instead of reading the prose line.
  - **Forward-only:** the check covers locks typed after you upgrade. Earlier failures have no recorded outcome and aren't listed.
