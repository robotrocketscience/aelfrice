### Documentation

- **PRIVACY.md lists the uv migration in setup as a default-on outbound path ([#1927](https://github.com/robotrocketscience/aelfrice/issues/1927)).** The one-shot uv-tool migration shared a row with `aelf upgrade` and was called an explicit command, but `aelf setup` runs it when the machine has no uv-tool install of aelfrice and `uv` is on `PATH`; `aelf setup --host codex` doesn't. It now has its own row and bullet as a fourth default-on path, and the onboard section names it. They say that it sends only package requests for aelfrice and its dependencies and downloads any of their files that uv's cache lacks. They also say that it installs every aelfrice command into uv's tool bin folder, writes `~/.aelfrice/migrated-to-uv` on success, and runs again only when both that file and the uv-tool install are gone. If aelfrice can't write that file, setup still reports success. The `aelf upgrade` row now says that the command makes an in-process GET to PyPI and installs nothing, so four rows, not five, reach the network through a program other than aelfrice. The update notifier runs its GET in a detached Python process, and the page now says so and says that the in-process grep finds that GET. The classify-orphans section now says what each path other than the two stored-content paths sends. The path count goes from seven to eight, and the default-on count from three to four.
