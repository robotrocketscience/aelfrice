### CI

- **The weekly mutation job runs as time-boxed shards, so it finishes and reports ([#1747](https://github.com/robotrocketscience/aelfrice/issues/1747)).**
  - **The cause:** every weekly run hit the job's 240-minute limit while mutmut was still generating mutants, so no mutant ever ran. `cli.py` alone produced 17,338 mutants in a 650 MB file that mutmut couldn't finish parsing. 6,137 of those came from `build_parser`, which is argparse declarations and help text.
  - **Shards:** `scripts/mutation_shards.py plan` counts each function's mutants with mutmut's own generator and assigns them to 8 shards of about 7,660 mutants each. A file with more than 4,000 mutants is split by function across shards. Files in `[tool.mutmut] do_not_mutate` are left out, as mutmut leaves them out. Each shard is its own matrix job, scoped with `only_mutate` and with `# pragma: no mutate block` on the functions of a split file that belong to other shards.
  - **Excluded:** `cli.py`'s `build_parser` is mutated in no shard. If it's renamed, the plan stops, and a test in the ordinary suite fails first.
  - **Time box:** `scripts/mutation_shards.py run` stops a shard's `mutmut run` after 330 minutes with SIGINT, then SIGKILL 2 minutes later. Not GNU `timeout`: mutmut rewrites its `.meta` result files in place, so a signal mid-write left a truncated file that `mutmut results` couldn't read. The supervisor keeps a copy of each whole `.meta` and puts back any file a signal truncated. A shard that runs out of time reports what it checked and warns. When the supervisor itself gets SIGINT or SIGTERM, it stops mutmut the same way. Once that stop begins, it ignores both signals until mutmut is killed and every `.meta` is repaired, so a second signal can't cut it short. Cancelling the job doesn't reach the supervisor: GitHub's runner signals only the step's shell and then ends the job, and a cancelled shard reports nothing.
  - **Checked:** a shard fails when it lists no mutant, or when no mutant was killed, survived, or timed out. `no tests` or `suspicious` on every mutant counts as checking nothing. It also fails when mutmut exits with anything but 0 or the time box's 124, because mutmut 3.8.0 exits 0 whether or not mutants survive, so any other status means it failed partway. Only the time box excuses mutants left `not checked`: a shard whose `mutmut run` exits 0 with any mutant `not checked` fails, because mutmut 3.8.0 can lose a worker error and still exit 0. The report uploads either way.
  - **Report:** a last job merges the shards' reports into one summary, and fails when a planned shard left no report, a shard listed more mutants than the plan gave it, or no shard checked a mutant. A shard that listed fewer mutants than planned, or a report for a shard the plan doesn't have, gets a warning in the summary.
  - **Contract:** the planning job first runs the tests that pin how mutmut 3.8.0 counts and skips mutants, against that exact version. In the ordinary suite they skip, because mutmut isn't installed there.
  - **Measured on GitHub:** a `workflow_dispatch` run on this branch planned 61,424 mutants and checked 57,955 of them in 5 hours 32 minutes: 41,176 killed, 16,750 survived, and 29 timed out. Six shards finished in 64 to 319 minutes with nothing left `not checked`. The other two reached the time box, stopped on SIGINT with no truncated `.meta` file, and left 1,307 and 1,325 mutants `not checked`. The report job merged all 8 reports.
  - **Measured locally:** the plan takes 38 s for 61,293 mutants, on an earlier `main`. After the pragmas, mutmut's own mutant count matches the plan for every file in every shard. Generating the largest piece of `cli.py` takes about 4 minutes, against more than 23 CPU-minutes for the whole file before.
