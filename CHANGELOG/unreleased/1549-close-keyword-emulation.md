### Fixed

- **The merge-train's auto-close now asks GitHub which issues a pull-request body closes, instead of emulating GitHub's Markdown reader ([#1549](https://github.com/robotrocketscience/aelfrice/issues/1549)).** Step 7/7 exists because this repo's signed-commit branch protection requires a fast-forward push, and a fast-forward does not trigger GitHub's own auto-close. [#1541](https://github.com/robotrocketscience/aelfrice/issues/1541) made the whole body reach the matcher; #1549 ruled that the step must read that body the way GitHub reads it. The first attempt at the ruling emulated the reading: a line-state scanner classified every line of the body as prose, fence, indent, quote or comment, and fired a keyword only in prose. **That approach is deleted.** Five review rounds each fixed one reading and found another block type, the last of them a wrong close on this repository's own pull-request template — a body with `## Linked issues` followed by an indented `Fixed #7` linked #7, while GitHub renders it inside `<pre><code>` and closes nothing. The same round found the scanner wrong after a setext underline, a thematic break, a GFM table row, an ATX heading and a block quote whose last block is not a paragraph. The surface being emulated was CommonMark's whole block grammar, so 172 lines of it — `_FENCE_RE` through `_reason_at`, the four scanning functions and the five line-state constants — went, rather than growing by one case per round.

  **What `scripts/merge_train_linked_issues.py` does now.** It renders the body through GitHub's own renderer, `gh api --method POST /markdown` with `{"mode": "gfm", "context": "OWNER/NAME", "text": <body>}` on stdin, and acts on the issue-link anchors GitHub itself produced. Text inside a fenced code block, an indented code block, an inline code span or an HTML comment never produces an anchor, so every block-classification question disappears at once instead of one per review round. GitHub anchors every reference and not only closing ones, so which anchor is a *directive* is decided by adjacency in the rendered text: for each anchor, the text immediately before it in the same block must end in one of the nine keywords — `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, in any case — optionally followed by a colon bound to the keyword and any whitespace. Adjacency is per block, so a paragraph, a heading, a table cell and a list item each stand alone; an anchor ends the run, which is GitHub's one-keyword-per-issue rule; and a keyword written inside a code span does not arm the anchor beside it.

  **The failure policy is loud, and closes nothing.** An unreachable renderer, a non-zero `gh` exit and a 200 carrying nothing all raise `RendererUnavailable`; `main` then prints two `error:` lines on stderr, prints **nothing** on stdout, and exits 2. Two alternatives were rejected in the module docstring rather than left implicit: falling back to a local parse is the emulation this change deletes and would make its wrong closes exactly when the renderer that would have caught them is down; and treating an unreachable renderer as "no links" is the silent no-op #1549 exists to kill, since the step would print what a body with no keyword prints. Closing nothing is recoverable by a human reading the step log; a wrong close is not. There is no retry, because this step runs after the merge has landed. `merge-train.yml` turns the non-zero exit into a `::error::` annotation naming the PR, replacing the `|| true` that used to swallow it, and the step log now has three distinct outcomes rather than two: `linked issues UNDETERMINED`, `no linked issues parsed from PR body`, and the close loop. Driving the extracted fragment under the step's own `set -euo pipefail` with a stub tool prints each of the three.

  **The renderer call is an injected seam, and the seam itself is tested.** `render_markdown(body, repo, *, run=None)` resolves `subprocess.run` in the function body rather than in the signature — a default argument is evaluated once, at import, so the signature form would bind the real runner past any replacement of it, and a suite that looked injected would reach GitHub on every run. That is not hypothetical: `test_the_render_seam_is_late_bound` failed against the live endpoint before the default moved. Tests pin the call twice. `test_the_real_call_is_pinned_argument_by_argument` injects the runner and asserts the exact argv, the exact JSON payload, `capture_output`, `text`, `encoding`, `check` and the timeout. `test_the_shipped_command_runs_gh_with_the_pinned_arguments` puts a `gh` of the tests' own on `PATH`, runs the shipped CLI end to end and reads back the argv and stdin that `gh` actually received. What GitHub renders is replayed from `tests/data/merge_train_github_renders.json`, five verbatim responses from the real endpoint; `scripts/record_merge_train_renders.py --dry-run` re-sends every body and reports any GitHub now answers differently, and reports `0 of 5 records drifted` on this tree. Running both suites with a poison `gh` first on `PATH` — one that exits 99 and prints `POISON` — still reports `168 passed`, so no test depends on the ambient `gh` or on the network.

  **The workflow needs no new permission, and this was measured rather than assumed.** `POST /markdown` against this public repository answers HTTP 200 with the issue-link anchors for an entirely unauthenticated request: `curl -sS -o /dev/null -w '%{http_code}' -X POST --data '{"mode":"gfm","context":"robotrocketscience/aelfrice","text":"Closes #7"}' https://api.github.com/markdown` prints `200`. The step already exports `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` and the job already declares `contents: write`, so nothing was added; the only workflow changes are the invocation, the annotation and the comments. Body size is not a constraint below the renderer's own cap — a 264,096-character body renders and links all three of its issues, checked with the `gh api --method POST /markdown --input big.json` command recorded in the module docstring; the cap itself is the next paragraph. Diagnostics still go to stderr only, because command substitution captures stdout and the shell splits it into the close loop.

  **The renderer has an input cap of its own, and on this step that has to be said out loud.** `POST /markdown` answers HTTP 403 `too_large` above 400 KB; a 420,000-character body reproduces it. That is a reintroduced input bound on the step whose defect *was* an input bound, so the entry says so rather than leaving a reader to find it: unlike `head -c 8192` it is loud — `gh` exits non-zero, `RendererUnavailable` is raised, and the failure policy above applies, so the step closes nothing and annotates. Can a pull-request body reach it? Not through the text. GitHub caps a body at 65,536 characters — widely reported as the 422 `Body is too long (maximum is 65536 characters)` and **UNVERIFIED here**, since measuring it would mean creating a pull request — which is at most 262,144 UTF-8 bytes. But it could reach the cap through the tool's own encoding, and did: `json.dumps` escapes an astral character to twelve ASCII bytes by default, so a legal 65,536-character emoji body became a 786,501-byte request and was refused, while the same body unescaped is 262,213 bytes and renders all three of its issues. `render_markdown` now passes `ensure_ascii=False`, which puts the cap beyond the reach of any body GitHub would accept, and names `encoding="utf-8"` on the call rather than inheriting the runner's locale, since the payload is no longer pure ASCII. `RENDER_LIMIT_BYTES` and `MAX_BODY_CHARACTERS` record both numbers so `test_the_largest_body_github_accepts_fits_inside_the_renderers_cap` asserts the relation instead of a reader trusting a paragraph.

  **The render says a reference exists; it does not say which object the reference named.** Review round six found a live wrong close. GitHub rewrites `Closes https://github.com/robotrocketscience/aelfrice/discussions/1549` into `<a class="issue-link" data-url=".../issues/1549">#1549</a>` — byte-for-byte what a plain `#1549` produces — so the shipped CLI printed `1549`, exit 0, empty stderr, and the train would have run `gh issue close 1549` on an unrelated issue. Discussions are numbered independently of issues and this repository has them enabled (`gh api repos/robotrocketscience/aelfrice --jq '.has_discussions'` prints `true`). The check cannot live on the render, which has already rewritten `data-url`, so `DISCUSSION_RE` scans the *source* body and `parse` hands the `(owner, repo, number)` triples to `close_directives`, which refuses any anchor resolving to one of them. The rule is deliberately blunt — a body writing both spellings for one number loses the close and gets a warning — because the module's standing asymmetry says a missed close is an open issue a human sees. **Every other URL shape was audited against the live renderer**, one `POST /markdown` per row, and each is ruled on in the docstring and replayed from a new `urlforms` record: `/issues/N` and `/pull/N` close N (pull requests and issues share one number space); `/issues/N#issuecomment-...` and `/pull/N#discussion_r...` close N, since the fragment names a comment *on* N; `/discussions/N` is refused; `/pull/N/files`, `/commit/SHA`, `https://github.com/orgs/ORG/discussions/N`, `/milestone/N`, `/projects/N`, `/releases/tag/...`, `/blob/...` and `/wiki/...` render ordinary links and are not references at all.

  **Two of the module's own rulings refused in silence, which is the one outcome AC5 forbids.** `Closes : #1549` and `Closes::#5` produced no stdout, no stderr and exit 0 — byte-for-byte what a body with no keyword produces, so the step logged `no linked issues parsed from PR body` and moved on, while the module docstring claimed every keyword found and not acted on prints a warning. `DECLINED_RE` now recognises an anchor whose preceding text ends in a keyword followed by nothing but colons and whitespace that `ADJACENT_RE` declined, and each gets its own `warning:` line with `DECLINED_SEPARATOR` as the reason. A form GitHub itself does not act on is still silent, because there is no close directive in it to report: `precloses #7`, `Closes issue #8` and `Closes#6` warn about nothing, and pinning that line is what keeps the warnings worth reading.

  **The adjacency window was an untested tuning constant that could invent a close.** `_TAIL` bounds how much text before an anchor the rule sees, and its comment invited a trim ("the rest is slack"). The window is a *suffix*, so `(?:^|\W)` could read the cut as the start of a block: at a six-character window a paragraph ending `... the last one is prefixed #7` closes #7, because `fixed` lands at position 0 and `^` stands in for the word boundary `prefixed` was supposed to defeat. The flip point is `len(keyword)` plus the trailing whitespace, so it differs per keyword — 6 for `prefixed`, 9 for `unresolved` — and `/usr/share/dict/words` holds 58 distinct words ending in one of the nine. A clipped window now refuses `^` and demands a real non-word character, which makes every match on the window a match on the whole run: clipping can lose a close, never invent one, and `_TAIL` is a cost bound rather than a ruling. Both directions are pinned — a sweep of every window size from 1 to 64 over six such words, a control that a real directive survives every window the bound allows, and the shipped value asserted against both a derived lower bound and a literal. The same pass found that the clipped flag had to come *back down* at a block boundary: left set, it makes the rule demand a non-word character that a block-opening `Closes #7` cannot have, and the close is lost in silence.

  **Two branches the review called dead, resolved one each way.** The reset on a non-issue-link `<a>` start tag is not dead, but its comment named the wrong case: a well-formed `[see](url)` is ended by `handle_endtag` anyway, and what the reset is actually for is an **unterminated** `<a>`, which `html.parser` never closes — without it `Closes <a href=...>` followed by an issue anchor arms that anchor. The comment now says so and the case is pinned. The `if tag != "br"` guard in `handle_startendtag` genuinely could not change any outcome — `br` is inline and is not `a`, so the synthetic end tag resets nothing — and is deleted; what remains is pinned on the self-closing spelling that is the only input reaching that handler, including a self-closing anchor that only the end-tag half records.

  **Two behaviours changed, both deliberately.** The tool now carries repository identity, because it must send a render `context` and GitHub returns a `data-url` on every anchor, so `--repo OWNER/NAME` (or `GITHUB_REPOSITORY`) is required and missing it is exit 2 rather than a guess. An anchor resolving to this repository is closed however it was spelled — `#N`, `GH-N`, `OWNER/NAME#N`, or a full `https://github.com/OWNER/NAME/issues/N` — because GitHub renders all four identically and closes all four. The emulating revision refused the last two indiscriminately, its own spellings included, only because it could not tell its own name from another's; that refusal is gone, and a link to a *different* repository is still refused out loud. A reference GitHub declines to render at all — `Fixes octo-org/octo-repo#100`, for a repository GitHub cannot resolve — leaves no anchor to hang a reason on, so a source-level scan reports it as `not linked by GitHub's renderer`. That scan is diagnostics only; it never decides a close, and it is not claimed to be a superset of what does, since `Closes *#7*` renders an armed anchor whose source the flat regex does not match. **Four divergences from GitHub remain and are stated in the module docstring**: commit messages are not read; cross-repository links are refused rather than followed; the pull request's target branch is not checked, since the train only ever fast-forwards `main`; and a block quote is refused although adjacency alone would close it — an anchor inside `<blockquote>` renders exactly like one in a paragraph, and refusing it is a ruling, made because a body quoting an earlier review comment that says `Fixes #N` is a real wrong close. That last one is an exact test on the rendered tree rather than a grammar to emulate, and dropping the `in_quote` branch from `close_directives` reverses it in one line. The three colon spacings — `Closes:#10` links, `Closes : #10` and `Closes::#10` do not — are rulings for the same reason: GitHub renders an anchor for all three and publishes no close processor.

  **Tests deleted, and why.** Every case that pinned the line-state scanner went with it: the fence-character and fence-length rules, the info-string rule, the unterminated-fence and unterminated-comment rules, the code-span-versus-comment ordering pair, the unmatched-backtick rule, the half-open-span end-offset rule, the eleven-row sweep of what may precede an indented code block, and the per-reason assertions that named `IN_FENCE`, `IN_INDENT`, `IN_SPAN` and `IN_COMMENT`. None of them describes code that still exists. What they were protecting — that a keyword GitHub reads as code closes nothing, and that the refusal is never silent — is pinned harder now, against GitHub's own recorded output rather than against a parser agreeing with itself. `tests/test_merge_train_linked_issues_1541.py` kept its offset cases and its truncation control and handed the question of which *forms* link to the #1549 module, since that is no longer a property of a regex this repo owns.
