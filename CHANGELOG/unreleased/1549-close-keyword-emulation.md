### Fixed

- **The merge-train's auto-close now reads a pull-request body the way GitHub reads it, and says so when it refuses a keyword ([#1549](https://github.com/robotrocketscience/aelfrice/issues/1549)).** Step 7/7 exists because this repo's signed-commit branch protection requires a fast-forward push, and a fast-forward does not trigger GitHub's own auto-close; [#1541](https://github.com/robotrocketscience/aelfrice/issues/1541) made the whole body reach the matcher and deliberately left two fidelity gaps open, because both change *which* issues close. The framing is now decided: **the step emulates GitHub.** `scripts/merge_train_linked_issues.py` matches all nine keywords GitHub acts on — `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved` — instead of the three the shell it replaced used, so `Fixed #N` no longer leaves an issue open that a merge commit would have closed. It also stops acting on a keyword a Markdown reader would not render as prose: inside a fenced code block (` ``` ` or `~~~`, three characters or more, an info string allowed, nested longer fences respected), inside an indented code block (four spaces or a tab), inside an inline code span, inside a block quote, or inside an HTML comment. The last two are not in the issue's list and were added because they are the same wrong close in a different costume: a body that quotes an earlier review comment containing `Fixes #N`, and a body that leaves a commented-out template line. An unclosed fence and an unclosed HTML comment run to the end of the body, as CommonMark specifies, and the choice is pinned rather than incidental — the two errors are not symmetric, since refusing a close leaves an open issue a human notices while making one closes an issue nobody asked to close. **The train can no longer fail silently.** A body whose only keyword the parser refused used to print exactly what a body with no keyword prints: empty stdout, empty stderr, and `no linked issues parsed from PR body` in the step log. Each refusal now emits one `warning: ignored "Closes #7" on line 4: inside a fenced code block.` line on stderr, naming the text, the line and the reason. stdout stays bare numbers because the workflow reads it into a shell variable and splits it on whitespace; running the step's own fragment locally confirms the warning reaches the step's stderr rather than the issue-number list, and `merge-train.yml` gained a comment and a test against anyone adding `2>/dev/null` or `2>&1` to that call. **Four divergences from GitHub remain and are stated in the module docstring** rather than left to be rediscovered: commit messages are not parsed, cross-repository links are refused rather than followed (but now refused out loud), the pull request's target branch is not checked — the train only ever fast-forwards `main`, so the condition holds by construction and nothing asserts it — and the block scan is line-based rather than a CommonMark parse, with the lazy block-quote continuation, list-relative indentation, cross-line code spans and cross-line keyword splits each named as the specific gap they are. `tests/test_merge_train_close_keywords_1549.py` holds **64 tests**, and every inert-body case asserts both halves — the inert keyword does not link *and* a second keyword in prose still does — because one half alone is satisfied by a parser that returns nothing. **Twenty-two mutations were run and all twenty-two go red**: narrowing the keyword set to three (13 failed), returning no inert spans at all (33), never opening a fence (18), never treating an indent as code (13), skipping the inline-span scan (2), treating a block quote as prose (3), skipping the comment scan (5), closing a cross-repository link locally (2), swallowing the rejections (5), printing them to stdout instead (5), letting an unclosed fence revert to prose (18), letting a closing fence carry trailing text (1), letting any fence run close any fence (2), letting an indent interrupt a paragraph (1), letting an unmatched backtick open a span (1), dropping the line number from the warning (3), adding `2>/dev/null` to the workflow call (1), reverting the docstring heading (1), re-adding "left for a decision" to the workflow (1), dropping the GitHub citation (1), dropping the regex's leading `\b` (4), and removing every stderr redirect from the workflow so the vacuity control fires (1). The tree was verified clean after each revert, and the two suites are green at 104 passed. Per the issue, `CONTRIBUTING.md` gains nothing: enumerating accepted spellings is what the *other* framing would have required.
