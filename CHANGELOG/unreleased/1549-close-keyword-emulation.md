### Fixed

- **The merge-train's auto-close now reads a pull-request body the way GitHub reads it, and says so when it refuses a keyword ([#1549](https://github.com/robotrocketscience/aelfrice/issues/1549)).** Step 7/7 exists because this repo's signed-commit branch protection requires a fast-forward push, and a fast-forward does not trigger GitHub's own auto-close; [#1541](https://github.com/robotrocketscience/aelfrice/issues/1541) made the whole body reach the matcher and deliberately left two fidelity gaps open, because both change *which* issues close. The framing is now decided: **the step emulates GitHub.** `scripts/merge_train_linked_issues.py` matches all nine keywords GitHub acts on — `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved` — instead of the three the shell it replaced used, so `Fixed #N` no longer leaves an issue open that a merge commit would have closed. It also stops acting on a keyword a Markdown reader would not render as prose: inside a fenced code block (` ``` ` or `~~~`, three characters or more, an info string allowed, nested longer fences respected), inside an indented code block (four spaces or a tab), inside an inline code span, inside a block quote, or inside an HTML comment. The last two are not in the issue's list and were added because they are the same wrong close in a different costume: a body that quotes an earlier review comment containing `Fixes #N`, and a body that leaves a commented-out template line. An unclosed fence and an unclosed HTML comment run to the end of the body, as CommonMark specifies, and the choice is pinned rather than incidental — the two errors are not symmetric, since refusing a close leaves an open issue a human notices while making one closes an issue nobody asked to close. **The train can no longer fail silently.** A body whose only keyword the parser refused used to print exactly what a body with no keyword prints: empty stdout, empty stderr, and `no linked issues parsed from PR body` in the step log. Each refusal now emits one `warning: ignored "Closes #7" on line 4: inside a fenced code block.` line on stderr, naming the text, the line and the reason. stdout stays bare numbers because the workflow reads it into a shell variable and splits it on whitespace; running the step's own fragment locally confirms the warning reaches the step's stderr rather than the issue-number list, and `merge-train.yml` gained a comment and a test against anyone adding `2>/dev/null` or `2>&1` to that call. The control that proves that test is not vacuous reads the same comment-filtered lines the test reads, because the new comment quotes both spellings and a whole-file search would otherwise report a redirect no command runs. **Four divergences from GitHub remain and are stated in the module docstring** rather than left to be rediscovered: commit messages are not parsed, cross-repository links are refused rather than followed (but now refused out loud), the pull request's target branch is not checked — the train only ever fast-forwards `main`, so the condition holds by construction and nothing asserts it — and the block scan is line-based rather than a CommonMark parse, with the lazy block-quote continuation, list-relative indentation, cross-line code spans and cross-line keyword splits each named as the specific gap they are. `tests/test_merge_train_close_keywords_1549.py` holds the cases (count them with `uv run pytest tests/test_merge_train_close_keywords_1549.py --collect-only -q`, which moves with ordinary edits), and every inert-body case asserts both halves — the inert keyword does not link *and* a second keyword in prose still does — because one half alone is satisfied by a parser that returns nothing. **Twenty-five mutations were run against the two suites and all twenty-five go red.** The per-mutation counts below were measured before the two review fixes recorded at the end of this entry, which raise the baseline and three of the counts; the direction is what they pin, and the baseline is whatever `uv run pytest tests/test_merge_train_close_keywords_1549.py tests/test_merge_train_linked_issues_1541.py -q` reports. Against the baseline of 107 passed as measured: narrowing the keyword set to three (13 failed), returning no inert spans at all (34), never opening a fence (19), never treating an indent as code (5), skipping the inline-span scan (2), treating a block quote as prose (3), skipping the comment scan (5), closing a cross-repository link locally (2), discarding only the spans an unterminated fence opened, so an unclosed fence reverts to prose while a closed one stays inert (2), letting a closing fence carry trailing text (1), letting any fence run close any fence (2), letting an indent interrupt a paragraph (1), letting an unmatched backtick open a span (1), widening an inert span to include its own end offset (2), swallowing the rejections (5), printing them to stdout instead (5), dropping the line number from the warning (2), leaving the rejection text unnormalised, so a match that spans a newline breaks the warning across two log lines (1), adding `2>/dev/null` to the workflow call (1), dropping the live `2>/dev/null` from the two other commands that use one (1), dropping the live `2>&1` (1), reverting the docstring heading (1), re-adding "left for a decision" to the workflow (1), dropping the GitHub citation (1), and dropping the regex's leading `\b` (4). Each mutation was reverted by rewriting the file from a saved copy of its original bytes rather than by `git checkout`, and the tree was verified clean after each revert. Per the issue, `CONTRIBUTING.md` gains nothing: enumerating accepted spellings is what the *other* framing would have required.

**A second blind review found two defects in the shipped parsing, and both are fixed here.** First, GitHub's own page — the one this module cites as its authority — accepts a colon after a closing keyword: "The keywords can be followed by colons or in uppercase. For example: `Closes: #10`, `CLOSES #10`, or `CLOSES: #10`." The regex required whitespace immediately after the keyword, so `Closes: #10` matched nothing, and matching nothing is indistinguishable from carrying no keyword: `parse("Closes: #10")` returned `([], [])`, the step printed `no linked issues parsed from PR body`, and the failure was the exact silent one the rest of this entry describes killing. The separator is now whitespace *or* a colon bound directly to the keyword. GitHub publishes the colon but not its spacing, so the module docstring rules on the three forms its examples leave open and the tests pin them: `Closes:#10` links, because the colon is itself the delimiter — which is why `Closes#10`, carrying none, still does not; `Closes : #10` does not link, because the colon has to touch the keyword; and `Closes::#10` does not, because it is one colon and not a run. **This knowingly admits a prose false positive, and the docstring records it rather than leaving it to be found.** A colon after one of the nine words is also how English introduces a list: merged PR #1504's body contains "All ruled prerequisites are closed: #1329, …", which now links #1329 against its author's intent. That cost was put to the operator and accepted, because GitHub closes #1329 from the same body on an ordinary merge and this step exists to reproduce the close the fast-forward push suppressed. It does not contradict the asymmetry above — "refuse rather than close" is the tie-break where GitHub's behaviour is undefined, and where it is defined and published, matching it wins. Second, **a wrong close in a context this entry already lists as excluded.** A body opening `<!--` on one line and writing `note -->` on the next, followed by a backticked `Closes #7` and a prose `Fixes #8`, returned `([7, 8], [])`: when a comment closed part-way through a line, the remainder was re-scanned for comments only and never for code spans, so the backticks around `Closes #7` marked nothing and #7 closed from inside an inline code span. The mirror was live too — comments were scanned before code spans on an ordinary line, so a `<!--` written between backticks opened a comment that swallowed the rest of the body and refused a prose `Fixes #8` as `inside an HTML comment`. Both are one bug: a code span and an HTML comment are inline constructs whose opening markers are ordinary text inside each other, so neither may be scanned as a pass before the other. A single left-to-right scan now takes whichever opens first and consumes it whole, and the remainder after a mid-line `-->` goes through that same path. Four new mutations cover the two fixes and each goes red on the tests that name it: dropping the colon from the separator (6 failed), restoring the comments-only scan of a post-comment remainder (1), making a comment always outrank a code span (2), and making a code span always outrank a comment (1). The three published mutants whose target code this restructure merged were re-measured against the new shape and all three went red harder than before, never softer: skipping the inline-span scan 2 → 5, skipping the comment scan 5 → 6, returning no inert spans at all 34 → 37. One existing assertion changed and was corrected rather than relaxed: `test_the_regex_keyword_set_matches_what_the_docs_claim` counted `|` over the whole pattern, a proxy for "the keyword alternation names nine keywords" that held only while the pattern carried exactly one alternation; the colon separator is a second, legitimate one, so the guard now reads the `keyword` group's alternation and compares it to `KEYWORDS` directly, which is the property it always meant.
