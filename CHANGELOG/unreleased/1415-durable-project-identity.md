### Fixed

- **Native Windows and WSL assigned two identities to one repository ([#1415](https://github.com/robotrocketscience/aelfrice/issues/1415)).** The `project_context` identity was a BLAKE2b digest of the absolute git-common-dir, and the two hosts spell one physical repository differently — `C:\tmp\aelfrice_identity_repro\.git` against `/mnt/c/tmp/aelfrice_identity_repro/.git` — so they minted `aelfrice_identity_repro-b0068862` and `aelfrice_identity_repro-74ec8541` **while reading and writing the same `memory.db`**. One repository's provenance split in two depending on which host a command ran from, and `AELFRICE_PROJECT_CONTEXT` filtering could hide rows written from the other. A sidecar beside the store now carries the answer: the first host to open writes it, every later host reads it. The seed is the **path-derived value rather than a fresh UUID**, which is what makes this migration-free — on the host that creates the file the identity is byte-identical to what it computed before, so rows already stamped with it stay reachable with no alias table and no backfill; the other host's spelling is appended once, so the split is recorded rather than silently resolved. Not `schema_meta.local_scope_id`, durable though it is: the identity is needed to *construct* the store, so reading it from inside that store is circular, and `store.py` defines that id as federation provenance. Fails soft to the old value on any I/O error — a read-only checkout must still open its store.
