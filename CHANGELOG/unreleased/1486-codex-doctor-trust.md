### Fixed

- **`aelf doctor --host codex` counted skills it never examined and approvals that were not ours ([#1486](https://github.com/robotrocketscience/aelfrice/issues/1486)).** Three defects in the trust half of #1430. First: `count_installed_codex_skills` globs `aelf-*` while `modified_codex_skills` iterates the *bundle*, so a marker-carrying skill directory for a slash command this build renamed or removed was counted as installed and never judged — the printed count ran one high, and the dropped command stayed invokable by the model until the next `aelf setup --host codex` pruned it. `orphaned_codex_skills` now reports that set and doctor exits nonzero on it, sharing its predicate with the prune loop in `install_codex_skills` so the set doctor names is by construction the set setup removes; both halves of that predicate are load-bearing, since name-membership alone sweeps in every current skill and the marker gate alone sweeps in a user's hand-authored `aelf-*` skill, which on the prune path means deleting it. The fault is gated on `owned_handler_count` like every other one — absent wiring stays exit 0 per the #1430 ruling — but the informational count line carries the orphan total unconditionally, because that line describes the directory rather than judging it, and a "0 orphaned" printed next to an orphan is the same class of untrue number this entry is about. Second: `approved [hooks.state] entries: N` counts every approved hook on the host. Codex keys those entries by a positional digest with no path back to a command, so no aelfrice-only subset can be computed, and filtering would mean building a matcher against a key format the Codex source marks for replacement. Per the operator ruling the line is relabelled rather than filtered or dropped — `entries: N (all hooks on this host, not only aelfrice)` — which keeps the diagnostic and makes the claim exactly true. The zero-approvals warning is untouched and stays sound: a foreign entry can only inflate the count, so zero is a true zero. Third, and a regression: #1427 replaced the module-level `AGENTS_SKILLS_DIR` with the late-bound `resolve_agents_skills_dir()`, and the #1427 entry lower in this section asserting that every reference was updated became false when #1476 wrote a new reference to the deleted name into `modified_codex_skills`'s default-dir branch. `modified_codex_skills()` with no argument therefore raised `NameError`. It was latent rather than live — the CLI always passes `skills_dir` and every test passes `tmp_path`, so the branch is unreachable today — but nothing gated on it either. Pyright strict *does* catch it (`reportUndefinedVariable`, 8 errors on the file with the line restored versus 2 pre-existing without), and `uv run pyright src/` is a checkbox on the PR template; no workflow runs it, so the undefined name reached `main` behind a self-reported tick. The end-to-end acceptance table from #1430 stays out of scope; it needs a reachable Codex model, which is `blocked:external` per #1217.
