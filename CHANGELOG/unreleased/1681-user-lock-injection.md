### Added

- **User locks reach your prompts in every repository ([#1681](https://github.com/robotrocketscience/aelfrice/issues/1681)).** A lock written with `aelf lock --user` now joins the L0 lock set next to the repository's locks. The SessionStart baseline, the UserPromptSubmit memory block and its `<locked>` section, the rebuild block that SessionStart injects after a compaction, the search-tool and agent-context hooks, and `aelf search` all inject it.
  - **Shared limits:** user locks count against the same token budget, relevance floor, and payload ceiling as repository locks. They don't get a budget of their own.
  - **Duplicates:** a user lock that near-duplicates a repository lock is dropped, and the repository copy is injected. The test is the one the `aelf lock` near-duplicate warning uses: Jaccard of at least 0.8 and Levenshtein ratio of at least 0.85.
  - **Marked in the output:** an injected user lock's `<belief>` element carries `scope="user"`, in the memory block, the baseline, the `<locked>` section, the agent-context block, and the rebuild block. A repository lock's element is unchanged. The retrieval token budget charges the attribute.
  - **Order:** repository locks come first, then user locks, each in its store's order (newest lock first, then by id). Two runs over the same stores inject the same order.
  - **Read-only:** the hooks open the user store read-only and never create it. They never write its database file, though SQLite can create the `-wal` and `-shm` files beside it. A process reuses what it read until the file changes; a write within the same timestamp tick that leaves the sizes unchanged can be missed until the next hook event. A missing user store changes nothing. A user store that can't be opened or read prints one warning to stderr, and the hooks inject the repository locks only. A user lock past its `--for` or `--until` window isn't injected, even before a write sweeps it.
  - **Benchmarks:** the retrieval benchmark, `aelf eval`, and the gap analysis in `aelf wonder` read the repository locks only, so their results don't depend on the user locks of the machine they run on.
  - **Commands:** `aelf search` tags a user lock `[user]` after its id, as `aelf locked` does, and its `--json` row carries `"scope": "user"`. `aelf show <id>` looks in both stores, counts partial-id candidates across both, and prints a `store:` line on each record once the user store takes part. `aelf feedback` on a user-lock id exits 1 and says feedback doesn't apply to user-scope locks, even when the repository has a belief with the same id; it changes neither store's database. `aelf feedback` now resolves a partial id the way `aelf show` does.
  - **No repository rows for user locks:** exposure rows, injection events, belief touches, and deferred-feedback rows skip user locks, including when the repository store holds an unlocked belief with the same text.
