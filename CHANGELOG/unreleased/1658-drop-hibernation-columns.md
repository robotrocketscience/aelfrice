### Removed

- **The store drops the unused `hibernation_score` and `activation_condition` columns from `beliefs` ([#1658](https://github.com/robotrocketscience/aelfrice/issues/1658)).** The two columns were the storage half of a hibernation lifecycle (v2.0, #196) that was never built: no code path wrote a non-NULL value, and measurement later found that a cold-decay sink does not help this workload. The first open after you upgrade runs two `ALTER TABLE beliefs DROP COLUMN` migrations, the same shape as the `demotion_pressure` drop in #814. Each drop rewrites the `beliefs` table, which took under 0.1 s per column on a copy of a 101 MB store. The `Belief` dataclass loses both fields, `aelf doctor --replay` stops comparing them, and the design memo moves to `docs/design/historical/hibernation_lifecycle.md`. **Upgrade note:** after you upgrade, restart any aelfrice process that is still running, including the sidecar warm-up process. A process running older code that already has the store open fails on its next belief read or write after the drop: a read raises `IndexError: No item with that key`, an update raises `no such column: hibernation_score`, and an insert raises `table beliefs has no column named hibernation_score`. A hook fire opens and closes the store, but three kinds of process hold it longer. The sidecar warm-up process is a detached child that a hook starts; it outlives the hook, holds the store open for its whole BM25F index build, and swallows its own errors, so its failure is silent. `aelf onboard` holds the store for its whole scan. Your own script can keep a `MemoryStore` open indefinitely. An older version that opens the store after the drop re-adds both columns as NULL and works. If two versions alternate on one store, for example an installed hook and a development checkout, each switch to the new version rewrites `beliefs` again. A switch to the older version only re-adds the columns and does not rewrite the table. At each switch to the new version, any older-version process that has the store open fails as described above. The #814 `demotion_pressure` drop had the same failure for a running process.
