### Added

- **The BM25 sidecar outcome is recorded per hook fire, so #1380's cold rate is counted rather than inferred ([#1407](https://github.com/robotrocketscience/aelfrice/issues/1407), [#1380](https://github.com/robotrocketscience/aelfrice/issues/1380)).** #1380 is priced on `cold_cost x cold_rate`. The 2026-08-06 re-derivation settled `cold_cost` (**2.89 s** cold first-fire at 44,668 beliefs, worse than the filed 1.45 s because the corpus grew) and left `cold_rate` resting on a **latency proxy** — classify a fire as cold at `latency_ms >= 1000`, giving 8.5% over 366 fires. The proxy is credible (its separating bucket is empty, and session-first fires are cold 21.3% against 5.9% for later ones) but it cannot attribute any individual slow fire to a rebuild rather than to SQLite lock contention, a cold page cache, or an unrelated stall, and the operator ruling of 2026-08-06 ~18:00Z is that #1380 must not be decided on it. `user_prompt_submit` audit rows now carry `sidecar_outcome`. **Three states, not the ratified boolean**, and that widening is the point: since #1199 shipped the incremental `update_from` path a stale sidecar no longer implies a full rebuild, so `fresh` / `incremental` / `full_rebuild` is what keeps #1199's 86.2% (*sidecar not fresh*) and the 8.5% proxy (*fire was slow*) from looking contradictory when they measure different events — a boolean would collapse exactly the distinction that explains them. Only `full_rebuild` is the term #1380 is priced on; `incremental` is cheap. **The value is recorded at the branch that was taken**, never re-derived at the audit site, and an AST guard over `BM25IndexCache.get` fails if an index-constructing branch is added without one — no behavioural test can cover that, since a branch nobody wrote a scenario for simply never runs. That guard now walks `orelse` and `finalbody` as well as `body`: it previously scanned `.body` only, so a bare rebuild in an `else:` arm left every test green, and the tests pinning the fix assert on the *block name* — a naive version of them passes under the very mutation they exist to catch, because the call-collector recurses the whole subtree. `_record_sidecar_outcome` also validates its argument against `SIDECAR_OUTCOMES` now, making the vocabulary a production contract rather than a test-only one; an unrecognised state would otherwise reach the audit log as a category no aggregator knows. **A fire is classified by its most expensive `get()`, not its last.** One fire can call `get()` more than once — a cadence-driven rebuild followed by the main retrieval is the case that exists today — and under last-write-wins that fire recorded `fresh` having just paid a full rebuild, at 74 ms so the latency proxy missed it as well. The one event #1380 is priced on was the one event the field failed to count. Latent only because cadence is default-off, and this field is meant to outlive that. **Absence is a distinct state and is an absent key**: a fire that never builds an index records nothing, and the committed `benchmarks/sidecar_rebuild_rate.py` excludes those rows and prints the excluded count rather than counting them as `fresh` — every fire logged before this field existed lacks the key, so folding them in would drive the measured rate toward zero purely as a function of how old the log is. On the current live log the script correctly reports **NO MEASUREMENT YET** rather than 0%. **The excluded rows are three populations, not one, and the script separates them**: the gate-skipped bucket is the largest and it is permanent, so one warning phrased as "wait for more data" over all of them would fire forever and name a cause that had stopped existing. Once any keyed row exists the unkeyed bucket splits further, into pre-field rows (which do shrink) and retrieval-ran-but-built-nothing rows (which do not), on a boundary derived from the earliest keyed `ts` rather than a hardcoded date; with no keyed row yet the script reports them as *unclassified* instead of guessing. **The rate is printed on all three denominators** — scored fires, measured retrieval fires, and all measured UPS fires — because `full_rebuild / scored` is *not* interchangeable with the 8.5% latency proxy it replaces: that proxy was computed over all fires, and `scored` holds only fires that did index work, so on a constructed log exercising all three states the two differ by **2.30x** (8.69% all-fires against 20.00% retrieval-fires). **That pair is a worked example, not a live measurement, and cannot yet be one:** the field is written only by this branch's code while installed hooks run the released package, so every `user_prompt_submit` row on the real log predates it. Verified rather than assumed — as of **2026-08-11** the live log holds **519 UPS fires across both rotations, 0 of them scored** (323 gate-skipped and keyless, 196 unclassified), and `grep -c sidecar_outcome` is 0 in each file. Read that as a reading with a date on it, not a constant: the log only grows, and the count moved between the review and this line. Reading one against the other turns a confirmation of the proxy into an apparent doubling. **Every denominator excludes the unmeasured rows.** Pre-#1407 and unclassified rows cannot enter the numerator, so keeping them under the line is arithmetically the same as scoring an unmeasured fire as not-a-rebuild — the bias the field exists to remove. Executed on the version that kept them: 50 pre-field rows against 60 scored with 10 rebuilds printed 9.09% against a true measured 16.67%, unwarned, because the caution keyed on `pre_field > scored`. Gate-skipped and no-index-work rows are *kept*: those are measured zeros, and a per-fire `cold_rate` needs them. **A gate-skipped fire is not automatically an unmeasured one**, either — the cadence dispatch runs above the shape gate and reaches `BM25IndexCache.get()`, so a fire the gate refused can still have paid a full rebuild; its audit row now carries the outcome instead of landing in the permanently-excluded bucket, which is the one place the expensive fires #1380 is priced on could hide. **And resetting the field costs the hook nothing.** The snapshot, the vocabulary and the recorder live in `aelfrice/sidecar_outcome.py`, a leaf module importing nothing outside the standard library. The reset has to run above the shape gate, and importing it from `aelfrice.bm25` there pulled numpy, scipy and snowballstemmer into every gate-skipped fire — reversing #1351 for exactly the population #1351 exists for, and aborting the whole hook body if the numeric stack were missing. A driven gate-skipped fire is now pinned in a subprocess to finish with none of the three in `sys.modules` and to still write its audit row when all three are unimportable; neither existing #1351 nor #236 test could see either failure, one probing only `import aelfrice.hook` and a driven `retrieve()`, the other returning at the `_IMPORTS_OK` guard ~100 lines above. #1380 is priced per-fire, so the all-fires figure is the `cold_rate` term. The no-argument invocation globs `hook_audit.jsonl*`, which includes rotated logs, so its totals span rotations — the docstring now says so. The test fixture is file-backed rather than `:memory:` because `sidecar_path_for` returns None for in-memory stores, which makes **the incremental branch specifically** unreachable; an in-memory fixture does observe two of the three states, so the narrower claim is the true one.
