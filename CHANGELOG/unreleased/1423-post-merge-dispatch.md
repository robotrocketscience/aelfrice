### Fixed

- **No `on: push` workflow had run since the merge train became the merge path ([#1423](https://github.com/robotrocketscience/aelfrice/issues/1423)).** `merge-train.yml` lands every merge as `git push origin "${HEAD_SHA}:refs/heads/main"` with `secrets.GITHUB_TOKEN`, and GitHub raises no workflow runs from events made with that token — the documented recursion guard, whose only exceptions are `workflow_dispatch` and `repository_dispatch`. Seven workflows carry a `push: branches: [main]` trigger and all seven share the same last push-event run, `3421cd73` at 2026-07-21T01:30:43Z; `main` has since moved **942** commits. For `codeql`, `deadcode`, `e2e` and `eval-calibration` the loss is the post-merge half only, since each also runs per-PR. For `release-drafter` and `flag-stale-open-prs` `push: [main]` is effectively the whole trigger, so they were not running late — they were not running, which is why release notes were being written by hand and why nothing had labelled a behind-`main` PR in 900+ commits. `zizmor`'s stop is older and unrelated: both its arms carry a `paths:` filter restricted to `.github/`, so its 2026-05-11 date is what a path filter produces, not what a recursion guard produces. The train now dispatches those workflows itself after a successful FF, which costs `actions: write` and no new secret. **A PAT or GitHub App token on the checkout was rejected**: it re-arms `on: push` for everything at once, but it puts a long-lived credential with write access to `main` in a repository whose entire merge model — FF-only, no bot rebase — exists because the bot deliberately holds no signing key. **A schedule was rejected** because it decouples the run from the commit that caused it, which is the one property `push: [main]` had. The dispatch list is **derived** by `scripts/push_trigger_workflows.py` rather than written into the workflow: a literal list is the same defect wearing a different hat, silently omitting the next `push:main` workflow anyone adds. `--ref main` and no inputs, because a dispatched run's check-runs attach to the head of the ref it was dispatched *on*, which is what keeps a post-merge run structurally unable to report against a commit it did not test (#1436/#1451). The fan-out is non-fatal — `main` has already advanced, so a failed dispatch warns rather than reddening a landed merge. Two consequences had to be fixed with it. `e2e`'s failure surfacing (#370) was gated on `github.event_name == 'push'`, so a red post-merge run would have opened no issue and labelled nothing — precisely the runs the step exists for; it now admits any non-`pull_request` event and reports the ref and event rather than asserting a push to `main`. And the stop was invisible for 942 commits because "no run" is an absence and every signal in the system was an absence test, so a weekly `push-trigger-heartbeat` workflow asserts presence: for each workflow in the same derived enumeration, the newest run on `main` by `push` **or** `workflow_dispatch` is compared against `main`'s head commit, and a lag over 14 days opens or updates one collated issue. `schedule` and `pull_request` runs are excluded deliberately — they are the masking that kept `codeql` and `zizmor` looking healthy throughout — and the lag is measured against the head commit rather than wall-clock so a genuinely quiet fortnight is not reported as a defect. Twenty mutations are checked, each red: dropping a dispatch hatch, dropping `actions: write`, hoisting the dispatch above the FF push or into `fail_and_unlabel`, retargeting `--ref`, passing an input, un-guarding the failure, hard-coding either consumer's list, reverting `e2e`'s guard, counting `schedule` runs as post-merge, measuring lag against wall-clock, tolerating an empty enumeration, and seven parser mutations. The push:main set is re-derived by a second, deliberately different in-test parse rather than compared against the script's own output, which is the tautological-guard failure of #1161.
