### Fixed

- **`setup` and `unsetup` refuse the options the `codex` host never reads, instead of accepting them and exiting 0 ([#1429](https://github.com/robotrocketscience/aelfrice/issues/1429)).** `aelf setup --host codex` hardcodes `scope="user"` into `install_codex_hooks` and reads only `--force` and `--codex-skills` off its namespace; `aelf unsetup --host codex` discards its namespace whole with a bare `_ = args`. The shared parser has no host-applicability boundary, so `aelf setup --host codex --scope project --settings-path /tmp/x --no-statusline --rebuilder` parsed, dispatched, wrote `$CODEX_HOME/hooks.json` at user scope, and returned 0 — a success report for five instructions that never reached the executor. Measured from the parser, 18 of `setup`'s options and 14 of `unsetup`'s are in that position. An explicitly supplied one now exits 2 with the offending option named, and it does so in `main` ahead of the auto-installer, the update check, and every executor, so nothing on disk has moved when the refusal prints. The disposition is refuse-all, with no per-option exemption: `--no-statusline` is refused even though the `codex` path installs no statusline, because an accepted option that does nothing is a false green even when the outcome happens to coincide with what you asked for. Making any of these options take effect is separate work and stays gated on a Codex host. The set is derived from the live parser rather than a second hand-kept list, so an option added to either subcommand falls under the gate the moment it is registered, and the explicitly-supplied test is a re-parse with every action default replaced by `argparse.SUPPRESS` rather than a scan of `argv` — argparse does the matching, so `--scope=user` and an unambiguous prefix such as `--proj` count exactly as they counted in the real parse. Defaults are untouched: `aelf setup --host codex` and `aelf unsetup --host codex` with no options still run the full install and teardown, and the default host is not gated at all. One first-party caller had to move with the fix. The generated `$aelf-setup` Codex skill mandates the `--host codex` form on every invocation and carried prose — "Opt out with `--no-pre-issue-guard`", "skip with `--no-statusline`", "`--rebuilder` (opt-in)", "Pass `--scope user` or `--scope project`", "`--settings-path PATH`" — that would have instructed a Codex agent to build a command line this gate refuses. `src/aelfrice/slash_commands/setup.md` is the single source for both hosts, so each of those mentions is now marked as claude-host guidance and a `codex`-host paragraph states what the host accepts and that it refuses the rest with exit 2. `tests/test_codex_option_rejection_1429.py` enumerates both halves from the parser: 51 refusal cases, one per option string including the `--no-` form of each `BooleanOptionalAction`, each asserting exit 2 with `hooks.json` and the skills directory still absent; and a scan of every generated skill that fails if any paragraph names a refused option without qualifying it as claude-host. Both isolation hazards are handled rather than assumed — the teardown resolves its skills directory through `Path.home()`, not `$CODEX_HOME`, so `HOME` itself is redirected and the omission control asserts the sandbox directory is the one reported, and `$CODEX_HOME` is created first, because setup exits 1 against a missing one and every case would otherwise pass for the wrong reason.
