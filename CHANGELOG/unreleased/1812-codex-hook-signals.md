### Added

- **Codex shows that aelfrice ran, and keeps its whole block in context ([#1812](https://github.com/robotrocketscience/aelfrice/issues/1812)).** Codex adds hook stdout to the model's context without showing it, and it saves any hook output over about 2,500 tokens to a file and gives the model only a preview. `aelf setup --host codex --status-message TEXT` now writes TEXT as the Codex `statusMessage` field of the retrieval, SessionStart, and stop handlers, where it used to exit 2 under #1429; the other claude-host options are still refused. Setup also writes `"additionalContextLimit": 9500` on the SessionStart, retrieval, and search-tool handlers, the 9,500-character bound aelfrice already puts on each hook's output, so Codex no longer cuts the block to a preview. A new opt-in, `[hook] summary_line` in `.aelfrice.toml` or `AELFRICE_HOOK_SUMMARY_LINE=1`, makes the Codex SessionStart hook print JSON: the same text as `hookSpecificOutput.additionalContext`, plus a `systemMessage` such as `aelfrice: 37 beliefs injected (37 locked)`. After a compaction the line also counts the beliefs in the rebuild block, and a fire that fails says `aelfrice: hook failed (DatabaseError)` instead of the empty-store line. It's off by default, and with it off the hook's stdout is unchanged. The hook learns it runs under Codex from a `--host codex` argument that setup now adds to the SessionStart command. Setup's SessionStart matcher is now `startup|resume|clear|compact|fork`, so a forked thread gets the baseline block; the earlier `startup|resume|clear|compact` left out `fork`. **After you upgrade, run `aelf setup --host codex` again** to write the new fields, argument, and matcher and to refresh the `$aelf-setup` skill, whose text now names `--status-message`. Then approve the changed entries with `/hooks` in a Codex session. Until you rerun setup, the hooks keep working as before, but `aelf doctor --host codex` exits 1, names `aelf-setup` among the installed skills that don't match this build, and reports the SessionStart group under the earlier matcher as a stale install that a setup rerun fixes. A SessionStart wrapper script that added its own `systemMessage` is no longer needed; `docs/user/INSTALL.md` describes how to remove it. `aelf doctor --host codex` now exits 1 when two or more handlers in one event have a command byte-identical to a command `aelf setup --host codex` writes for the same aelfrice program, because Codex then starts that command once for each copy that it doesn't skip. Codex skips a handler that a `[hooks.state]` entry disables and one that you haven't approved with `/hooks`, so doctor counts a copy only when the `trusted_hash` of its `[hooks.state]` entry in `config.toml` equals the hash Codex computes for the handler now, which doctor computes the same way. A copy that you haven't approved, that changed since you approved it, or whose hash doctor can't compute with certainty counts no run. When one fire runs it beside another copy, it gets a `[warn]` line that says Codex starts the command twice once both copies are approved. This holds in `hooks.json` and in the `[hooks]` table of `config.toml` alike, so two approved copies that only `config.toml` holds fail doctor with no aelfrice handler in `hooks.json`. Doctor compares commands character for character with what setup would write now, at any install path, and reads no shell syntax. It compares only handlers whose `type` is `command`, and on Windows it compares `commandWindows`, or its alias `command_windows`, when a handler has one, because Codex runs that field there instead of `command`. Every other handler that contains the name of a program the package installs anywhere in any of its strings, in any case, gets a `[warn]` line that names the handler, including the hook programs setup doesn't write for Codex and the `aelf` CLI, which counts only as a word, and the duplicate check doesn't fail on it. The older check for a program that isn't on disk still fails doctor for an aelfrice handler in `hooks.json` whose program path is gone. That includes `/usr/bin/env aelf-session-start-hook` beside the handler setup writes, `env -Saelf-session-start-hook`, `${CMD:-aelf-session-start-hook}`, a `python3 -c` script, a command substitution, a `PATH` setting, a redirect, a command that only prints the name, such as `echo aelf-session-start-hook`, and a name that shell quoting splits, such as `aelf-sess''ion-start-hook`: before it looks for a name, doctor deletes each backslash-newline pair and each `'`, `"`, `\`, `` ` ``, and `^`. Only a name that the command builds at run time, or a program reached through a link with another name, escapes the warning. It also includes a field Codex doesn't run, such as `statusMessage`, a handler or group written as an array, which Codex reads by position and in which doctor counts no run, and a handler that an older install wrote at another path; under an event setup writes in `hooks.json`, the line says a rerun of `aelf setup --host codex` replaces it. A copy of setup's command under an event where setup writes no handler of that program, such as the `aelf-hook` command under SessionStart, counts as a run there and gets a `[warn]` line as well. Doctor reads the `[hooks]` table in `config.toml` as well as `hooks.json`, because Codex loads and runs the handlers in both, so a copy of setup's handler in `config.toml` counts as a second run. Doctor counts handlers only under the event names Codex reads, so a handler under another key, such as `Notification`, adds no run, and a handler there that names an aelfrice program gets a `[warn]` line. When Codex rejects all of `hooks.json` or all of the `[hooks]` table, for example over a handler with no `type`, an unknown `type`, a `command` handler with no `command`, or both `commandWindows` and `command_windows`, it loads no hook from that file. Doctor then counts nothing in it, says so in a `[warn]` line, and exits 1, as it does for a `hooks.json` that isn't valid JSON. Two handlers count only when one fire runs both, and doctor counts a run only in a group whose matcher it reads: an empty, missing, `*`, or `.*` matcher, a list of exact names, or names joined by `|` with optional `^` and `$` anchors, such as `^res|fork$`, forms that mean the same thing to Rust's `regex` crate and Python's `re`. In SessionStart, PreCompact, and PostCompact, the matcher matches the session source or the compaction trigger, so a copy under a `fork` group counts beside setup's handler. In PreToolUse and PostToolUse, groups that list exact tool names, or names that each have both `^` and `$`, count together only when one tool call matches both, where `apply_patch` also matches `Write` and `Edit`, and `spawn_agent` also matches `Agent`. In the events Codex fires when an agent thread starts and stops, groups that list exact names count together only when they share a name. Doctor counts no run in a group under any other matcher, such as `^[[:alpha:]]+$`, `(?i)fork`, or one that Codex can't compile, and none in SessionEnd or PermissionRequest, whose matcher values doctor doesn't list. Each handler there that names an aelfrice program gets a `[warn]` line instead, so doctor exits 0. A TOML date or time, such as `matcher = 1979-05-27`, is text to Codex and matches nothing, so doctor counts no run under it, and on Windows a `commandWindows` written as one is what Codex runs, so doctor doesn't count the handler's `command` there. Doctor scores a plain `codex` launch, which reads `config.toml` and no profile file. It counts no run while that launch starts no hook: when `[features]` in `config.toml` sets `hooks`, or its earlier name `codex_hooks`, to false, or when Codex refuses to start, over a top-level `profile` key, a `[features]` value that isn't true or false at the top level or in a `[profiles.NAME]` table, under any key that Codex doesn't read as a table of its own, `tool_registry = true`, a `[hooks]` table it rejects, or a `config.toml` that isn't UTF-8 or that its TOML parser rejects. It also counts no run, and says why, while such a `[features]` table holds a table or another value that isn't true or false under a key Codex reads as its own, such as `[features.code_mode]`, because doctor doesn't check those values. It also counts no run for a handler whose `[hooks.state]` entry in `config.toml` sets `enabled = false`. Doctor reads `enabled` and the approval under the one key Codex reads, whose path starts with the Codex home in its canonical form when `CODEX_HOME` is set, as `realpath(3)` gives it, which on macOS also corrects letter case, and as written, made absolute, when it isn't set or is empty, so an entry under another spelling, such as the target of a symlinked `~/.codex`, disables and approves nothing, and a later entry for the same trimmed key wins. A profile file, `$CODEX_HOME/NAME.config.toml`, whose `[features]`, `[hooks.state]`, or `[hooks]` changes which hooks `codex --profile NAME` starts, or that doctor can't read, and a `[profiles.NAME.features]` table that sets `hooks`, which no launch reads, get a `[warn]` line that names the profile and leave a failure for the plain launch in place. Each such handler that names an aelfrice program gets a `[warn]` line that says why. After these checks, doctor reads every string in `hooks.json`, all of `config.toml`, and each profile file, keys and values to a depth of 256, so a program name in `notify` or `mcp_servers.NAME.command` gets a line too, and gives each one that names an aelfrice program and that no other line covers a `[warn]` line with the file and the string's path, such as `hooks.Bogus.hooks[0].command`. Only the commands of setup's own handlers are left out. Doctor counts no run in a file that holds a group or a handler written as an array under an event name, because it doesn't check that shape and so can't tell whether Codex loads the file; there the last check warns about setup's own commands too. Codex rejects a `hooks` value in `config.toml` written as an array, and a malformed `[hooks.state]` entry, so doctor exits 1 on them, as it does for any `[hooks]` table Codex rejects. Doctor also exits 1 on a `hooks.json` with an array or object 128 levels deep, where serde_json stops, or with a lone UTF-16 surrogate escape in a key or value Codex reads, and on a `config.toml` whose arrays and inline tables nest more than 80 levels deep or that has a key of more than 80 dotted parts, or that holds an integer outside the 64-bit signed range or a float that overflows, such as `1e400`, which Codex's TOML parser rejects whole, so Codex refuses to start and doctor counts no run in any file. A `hooks.json` that isn't UTF-8 loads no hook and exits 1 the same way, a `config.toml` that isn't UTF-8 makes Codex refuse to start and exits 1, and doctor no longer raises on either, on a profile file that isn't UTF-8, on an integer longer than Python reads in any of these files, on a Codex home it can't list, or, on Python 3.12, on a `~/.agents/skills` or a `CODEX_HOME` under a folder it can't search. Doctor reads files of any depth without raising `RecursionError`, and serde skips a value under a key Codex doesn't read at any depth, so doctor reads that file and names the part it left out. The `[warn]` line says the handler may also run the program when one fire runs it beside another handler of the program, and otherwise says that doctor can't tell whether it runs the program and that setup's handler is the supported form. Doctor removes one UTF-8 byte order mark from the start of `config.toml` and of each profile file, as Codex's TOML parser does, and reads the file with `tomllib`, so when the file uses TOML 1.1 syntax that Codex reads, such as a trailing comma in an inline table, doctor counts no run in any file, because it can't read the approvals, and gives each line that names an aelfrice program a `[warn]` line with its line number. Doctor rejects a `hooks.json` holding `NaN`, `Infinity`, or `-Infinity` at any place, as Codex does, and exits 1. Codex reads `hooks.json` with serde_json's `arbitrary_precision` feature, so a number a 64-bit float can't hold, such as `1e400`, loads where Codex skips the value and rejects the file in a typed handler field such as `timeout`, and doctor counts and rejects the same way. Where doctor counts no run because it can't tell whether Codex starts or loads the file, each copy of one of setup's commands in an event that holds two or more gets a `[warn]` line that names the event and the program. Codex doesn't expand a `~` at the start of `CODEX_HOME`, so doctor and unsetup read such a value as a path under the current folder, as Codex does, and no longer raise for a `~user` that doesn't exist, and `aelf setup --host codex` exits 1 for it, writes nothing, and asks for the expanded path. Doctor reads only the user layer of Codex's configuration, `hooks.json` and `config.toml` in `$CODEX_HOME`, so `/etc/codex/config.toml` and the `.codex/` folder of a trusted project can add handlers or turn hooks off without doctor seeing them. A `[hooks]` table that Codex rejects makes Codex refuse to start, so doctor counts no run in `hooks.json` either.
