### Fixed

- **uv-tool detection now resolves uv's tools directory instead of assuming one ([#1431](https://github.com/robotrocketscience/aelfrice/issues/1431)).** `_running_from_uv_tool`, `_is_uv_tool_install` and the reachable-install inventory all hard-coded `~/.local/share/uv/tools`, so a normal **Windows** uv-tool install was classified `non_uv` and `aelf upgrade-cmd` recommended `pip uninstall -y aelfrice && uv tool install aelfrice` — advice that invokes an unrelated pip. Resolution now matches uv's own: `UV_TOOL_DIR` wins outright, else tools sit in a `tools/` subdirectory of uv's persistent data directory — which is `$XDG_DATA_HOME/uv` (falling back to `~/.local/share/uv`) on Linux/macOS but `%APPDATA%\uv\data` on Windows, so the Windows default is `%APPDATA%\uv\data\tools` and carries a `data` component the POSIX one does not. The strongest signal is uv's own receipt — `uv-receipt.toml` sits at the root of every tool environment, and for an installed tool that root *is* `sys.prefix`, so the running environment identifies itself with no assumption about locations. The converse now holds too: **a directory named `aelfrice` without a receipt is no longer read as a uv install**, because recommending `uv tool upgrade` for a left-over directory hands the user a command that cannot work. Ancestry replaces the string-prefix compare, and `_which_all_aelf` — which looked for a bare `aelf` and required an executable bit Windows does not have — now consults `PATHEXT`; the venv-hosting suppression follows it to `Scripts`, so `uv run` in a project tree no longer reports its own venv as a second install. The classifier and the reachable-install inventory share the **receipt predicate**, not merely the directory resolver, so one directory can no longer be `non_uv` to the upgrade advice and a `uv_tool` site in the multi-install warning at the same time. **Auto-install stays shut on Windows** behind an explicit `os.name` check: a correct classifier would otherwise open that gate for the first time and let `aelf` rewrite `~/.claude/settings.json` on a platform where the hook commands it writes resolve through a `bin` literal that is a no-op there.
