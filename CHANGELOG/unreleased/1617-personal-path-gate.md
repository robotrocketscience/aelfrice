### Fixed

- **No gate caught an absolute home path, nothing stopped a host configuration directory being tracked, and nothing refused a personal identity in commit metadata ([#1617](https://github.com/robotrocketscience/aelfrice/issues/1617)).** PR #1610 added `.gemini/settings.json` to this public repo carrying a developer's absolute venv path twelve times, and `secrets-scan`, `pattern-scan` and `history-scan` all reported PASS. The first looks for credentials, and an absolute path is not one; the other two match against patterns held in the `SCAN_RULES_B64` repository secret, which — established by behavior, since the secret cannot be read — carries no home-directory rule. A sweep of the tree found the same class of disclosure already on `main`: `docs/design/hook-injection-audit.md` carried a real `/Users/<user>/` path in two table rows, landed 2026-07-20 and still live. Both rows now use the `~/` form the same document already uses elsewhere. **Removing them clears `HEAD` only — git history retains the old blobs, and the content pushed to `refs/pull/1610/head` stays reachable regardless of the branch deletion, because GitHub pins pull-request commits permanently.** Only GitHub Support can purge that ref.

  The same sweep found a worse disclosure that no gate covered: **two commits on `main` carry a contributor's real name and corporate email as the git author**, from a machine whose `user.email` was never set to the privacy form. Across the same 367-commit window, 364 commits use `<id>+<login>@users.noreply.github.com` and one is Dependabot. Commit metadata is the least recoverable disclosure there is — copied into every clone and fork, served by the unauthenticated REST API, and pinned by the pull refs, none of which a history rewrite reaches. `scripts/check_commit_identity.py` refuses it at the push, which is the only control that works. It checks the **name as well as the address**: GitHub's no-reply forms anonymise the address and do nothing about `%an`, and the commits that motivated this carried both.

  Two design choices are deliberate. The rules live **in the tree rather than in a secret**, because a gate whose patterns nobody can read is a gate nobody can audit, test, or regression-guard — the reason this gap stayed invisible until something went through it. And the path checker covers **both halves** of the failure: the path text is the disclosure, but the untracked-but-unignored host dotdir is the vector. `.gitignore` had no rule for `.claude/`, `.gemini/` or `.codex/`, and this repo's own worktrees live under `.claude/`, so the directory sat one `git add -A` from being staged. All three are now ignored, refused if tracked at **any depth**, and added to the pre-push hook's banned paths, which previously knew only about `.claude/`.

  Verified rather than asserted. Against the #1610 diff the path checker flags **12 added lines**, every one of which the three shipped scans passed; the identity checker flags the two offending commits on both name and address. Across all **1,145** tracked files the path checker reports **zero** false positives, and the allowlist that keeps `/home/runner`, `/Users/synthetic`, `C:\Users\ci\` and the container service accounts quiet is visible in the diff rather than in a secret. Refusing the synthetic fixture names this tree already uses (`dev`, `alice`, `first`, single-character segments) was measured and rejected: it flagged 61 legitimate lines across 20 files, and a gate that noisy gets switched off. That hole is recorded in the source beside the allowlist rather than left implicit.

  **The suites drive the scripts, not just the patterns.** An earlier revision tested the regexes alone and was vacuous over the thing that matters — nine mutations survived it, including `main()` returning 0 and `scan_tracked()` returning nothing, either of which turns the required CI step into a no-op while every test passes. A gate whose suite cannot detect the gate's own removal is the #1610 failure mode one layer up. The arms now run the real scripts against real dirty repositories and assert on exit codes; **all 23 mutations are killed**, including every one that previously survived.

  Escape hatches exist on purpose: a `pii-allow` marker on a line, or a glob in `.github-pii-exempt`. A gate with no override gets disabled wholesale, and both of these are visible in review where a silent bypass would not be. In the same spirit, three entries left the pre-push hook's `BANNED_PHRASES` — each named something this repo already publishes itself, so they protected nothing while forcing an override to write ordinary prose about our own CI.

  **Where it runs, precisely.** In CI: inside `pattern-scan` and `history-scan`, both required, plus the tests under the required `pytest` legs. Before a push: `.githooks/pre-push`, which is tracked, so a checkout that has run `scripts/setup-hooks.sh` gets the checks on its next pull. A disclosure failure there is deliberately **not** waivable by `ALLOW_STALE_BRANCH_PUSH`, which exists to wave through a branch that is merely behind main. `scripts/install-discretion-hook.sh` also carries them, but note that it is an *installer*: it writes a copy into `.git/hooks/pre-push`, so on a machine that uses that copy the new checks go live only after re-running it with `--force`. CI gates regardless.

  What it does not cover: content already in git history or in a `refs/pull/*` ref; a home path whose user segment is an allowlisted name; paths in binary files; a personal path in a commit *message*; and anything outside the `/home/…`, `/Users/…` and `X:\Users\…` shapes. This catches one high-frequency disclosure, not PII in general.
